upstream-excerpt-profile.txt -- the evidence the GM7MG7P platform
profile is built on
========================================================================

The committed source of every upstream spelling `profile-map.csv` cites and of
every `#define` the patch in this directory uses. The `gm7mg7p-dmi-entry`
excerpt beside this one covers the feature bits, the cTGP block, the charge
block and the DMI table, and contains **none** of what this patch is built on
-- checked for `0x0751`, `0x0782`, `0x0742`, `MANUAL_FAN`, `DEFAULT_MODE`,
`PERFORMANCE_MODE`, `0xB0` and `platform_profile`, the only hit is
`KBD_TURBO_LEVEL_MASK`. This file is the other half, and
`tools/check_power_profile.py` checks the map and the patch against it byte
for byte so a reviewer can do that offline, with no network and no re-fetch.
`fetch-upstream-profile.sh` re-derives the fragments below from a fresh fetch
to prove they are still what the source says.

The `uniwill-acpi.c` digest is the one worth failing on, and only that one. A
git tree at a fixed rev is immutable, so a re-fetch must reproduce it. The
**tarball's** hash is recorded as an observation and nothing is failed on it,
because it is not a stable artifact: codeload regenerates the archive, and
`gm7mg7p-dmi-entry/upstream-excerpt.txt` records two fetches of this same rev
on the same day returning 27,634 and 27,605 bytes with different digests while
`uniwill-acpi.c` came back byte-identical both times. The 27,605-byte figure
here is the same second one, re-fetched independently for this directory.
Pinning the tarball hash would fail a re-fetch for a reason that has nothing to
do with the source having changed.

`uniwill-acpi.c` is GPL-2.0-only; see the `MODULE_LICENSE` line at the foot of
this excerpt and `LICENSE` in the fetched tree. It is quoted here as the
evidence a claim is checkable, in fragments small enough to review in a diff.
The full 90 KB file is deliberately *not* vendored; `fetch-upstream-profile.sh`
is how to get all of it.


THE FINDING THAT CHANGED THE SHAPE OF THIS WORK
-----------------------------------------------

**Upstream has no platform-profile support at this rev.** The plan issue #102
was written on the assumption that it did: it asked for a `platform_profile`
handler written against "the `platform_profile` struct, the
`UNIWILL_PLATFORM_PROFILE_UNK`/low-power/balanced/performance enum and the
existing profile store/cycle helpers". None of the three is present at this
rev, on the two measurements below, which are of different weight.

  - `struct uniwill_device_descriptor` is quoted in full at 428-436 below --
    five members, closing brace included -- with no `platform_profile` member
    in it. That is the struct the callback would go in, read rather than
    searched for, and it is the quotation that establishes the missing member.
  - A scan for the names, which is a scan of four spellings and not a reading
    of the file:

        $ grep -rn 'platform_profile\|PLATFORM_PROFILE\|profile_cycles\|profile_available' .
        (no output)

    run over the whole extracted tree, every file of it. So: none of those
    four names occurs anywhere at this rev. That is what this measurement
    shows, and it is not on its own a statement about functionality the scan
    did not look for.

What *is* there is the one line quoted at 470-482 below, commented
"Reported when user wants to cycle the platform profile" and mapped to
`KEY_F14` -- an event with nothing to cycle. So the patch in this directory
has to add the framework, not only a callback, and every one of the the
three names above is a name this patch introduces rather than one it reads.

Two consequences, both recorded rather than smoothed over:

  - The patch is larger than the issue asked for, and the upstream PR body says
    so in its own first paragraph instead of letting a reviewer discover it.
  - The plan's "the existing profile store/cycle helpers" is not a thing the
    excerpt can quote, so this excerpt does not quote one. The two things a
    handler is written *against* -- `EC_ADDR_MANUAL_FAN_CTRL` with its
    `FAN_MODE_*` bits, and `EC_ADDR_BIOS_OEM_2` with `DEFAULT_MODE` -- are at
    181-190 and 240-254, and those are what the map cites.

One more thing the fragments are here to show, because it is easy to miss and
it decides whether the patch applies at all: the regmap is gated. Every
address has to be added to `uniwill_writeable_reg` (597-612),
`uniwill_readable_reg` (626-640) and, for anything the EC may change under
the driver, `uniwill_volatile_reg` (674-690) before a `regmap_read` or
`regmap_write` of it returns anything but `-EIO`. `0x0751`, `0x049F` and the
PL default blocks are in none of the three at `5a24248`. The patch adds them;
a handler that skipped the gate would compile, apply, and write nothing.
