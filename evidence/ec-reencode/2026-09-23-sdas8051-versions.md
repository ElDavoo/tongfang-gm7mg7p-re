# The re-encode under two SDCC builds (2026-09-23, issue #157)

The `ec/ghidra/reassembly.csv` tallies are one assembler's. This is the second
measurement, taken with the `sdas8051` that
`.github/actions/project-setup` installs on a GitHub-hosted runner, and the
row-by-row comparison between the two. Read with `docs/findings.md` §14h.

No hardware, no Windows, no Ghidra, no network. `build_images()` needs the
committed firmware and `make_bank_image.py`, and that is all of it.

## The environment, captured before the run

PATH, and the point is to exercise the PATH entry project-setup installed.

All 2,705 `listing_digest` values are identical on both sides, so both runs
read the same listings.

The 52 differing rows are in
**`2026-09-23-sdas8051-rowdiff.csv`**, committed rather than pasted here.

Two things moved and one did not, and the split is the useful part:

- **The unencodable set did not move.** No row's `instructions_checked` or
  `instructions_unchecked` changed, and both sides total 45,394 and 143. Those
  two columns are computed by `to_sdas()` in pure Python, before the assembler
  is invoked at all, so they are a property of the committed listings and this
  tool's own gap rules — not of which ASxxxx happens to be on PATH.
- **The outcome set did move, by 52 rows, all in one direction.** Every one of
  the committed report's 58 `assembler-gap` rows is accounted for: 47 re-encode
  completely under the apt build, 5 re-encode with the same 143 unchecked
  instructions between them, and 6 stay gaps. None regressed. The 6 that stay
  are the `ajmp` rows (`GAP_MNEMONICS`, a tool-side classification both builds
  are asked to honour, so they are gaps by construction rather than by
  measurement).

The 52 rows' committed `detail` is `no bytes emitted at NNNN`, and the
instruction at each named address is an ordinary one — `mov` (28), `lcall` (7),
`movx` (4), `clr` (3), `ret` (2), `ljmp` (2), and six singletons (`add`,
`movc`, `setb`, `inc`, `subb`, `push`). An assembler declining to place a
`movx @DPTR,A` at the first instruction of a function is not a statement about
the form.

## Which of the two causes it is, is not settled here

Two candidate causes for the 52, and this environment cannot separate them:

1. **A different assembler.** SDCC 4.2.0's `sdas8051` may accept forms
   05.50.4 declines.
2. **A race in `verify()` that was live when the committed report was made.**
   See below. `08b72e2`, the commit that wrote the report, records no `--jobs`
   value, so there is no way to tell from history whether the run was
   serialised.

Re-running the nix assembler would settle it, and nix is not something
project-setup installs. That is the follow-up, named in §14h.

## The race, and what it did to the numbers

The first five `--jobs 4` runs of the command in the diff above did not agree
with each other. The `assembler-gap` column alone took five values:

```
run 1:  match 2584  partial 76  gap 42  assembler-error 2  mismatch 1
run 2:  match 2590  partial 72  gap 42  assembler-error 1
run 3:  match 2593  partial 74  gap 37  assembler-error 1
run 4:  match 2567  partial 73  gap 65
run 5:  match 2577  partial 73  gap 53  assembler-error 2
```

and the `--jobs 1` run gave the same answer twice:

```
2621 match, 78 partial, 6 assembler-gap   (5.57 s, 5.53 s)
```

The instruction columns were 45,394 / 143 on every one of those runs, racy or
not. The function outcomes are the only thing that moved, and they are exactly
the columns that depend on the assembler process actually completing: a row
whose `.s51` gets overwritten by a concurrent row reads back a listing that is
not its own, and reports `no bytes emitted` for an address the assembler did
place.

The cause was in `verify()`'s dispatch. It allocated one scratch directory per
worker and then indexed that list by **row** (`dirs[idx % jobs]`), which is not
the same thing: `ThreadPoolExecutor.map` hands the next row to whichever worker
frees up first, so rows 0 and 4 can be in flight together and both took
`dirs[0]`, overwriting each other's `f.s51` before reading back a `f.lst` that
was not their own. The comment above the line said "one scratch dir per
thread", so the intent was right and the implementation was not. The fix is a
`threading.local()` directory allocated on each worker's first row, asserted by
a self-test that forces the pickup order which provokes the collision rather
than waiting for it to happen by luck.

After the fix, three `--jobs 4` runs of the same command produced three
byte-identical CSVs, and equal the `--jobs 1` result. All the numbers in this
file are from the post-fix run.

## Reproduce

Needs an `sdas8051` on PATH, and nothing else:

```
$ sdcc --version && command -v sdas8051 && readlink -f "$(command -v sdas8051)"
$ sdas8051 | head -2                      # the banner, for the record

$ scratch=$(mktemp -d)
$ unset SDAS8051                         # exercise the PATH one, not an override

# The command .github/scripts/agent-gates-deep.sh runs, read-only, no --report:
$ python3 ec/tools/verify_reassembly.py --work "$scratch/reasm" --jobs 4

# The per-row side of the comparison. Refuses ec/ghidra/reassembly.csv:
$ python3 ec/tools/verify_reassembly.py --work "$scratch/reasm" --jobs 4 \
      --emit-csv "$scratch/reasm.csv"

# The committed report is not a writer of the comparison:
$ git diff --stat ec/ghidra/reassembly.csv   # no output
```

## What this record does not establish

- **That the two builds produce the same re-encode.** They measurably do not:
  52 rows differ, and both differences are recorded above.
- **That they are equivalent.** 2,705 rows through one tool is a measurement of
  this corpus, not a generalisation about two ASxxxx versions.
- **Which build is right about the 52 rows.** The apt build emits bytes that
  match the firmware for all 52, which is a statement about what this
  firmware holds. It is not by itself a claim that 4.2.0 is the better
  assembler, and the 47 `match` rows are not new evidence for the 1:1 claim:
  the committed report already asserts those bytes are what the firmware holds,
  and the byte check (`--check`, no assembler) covers all 45,537 instructions
  either way.
