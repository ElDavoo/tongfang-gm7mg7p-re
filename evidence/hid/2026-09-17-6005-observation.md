# 048d:6005 live static-colour test — human observation

Related issue: #5. Physical GM7MG7P, Linux 7.2.6.
Machine log: `2026-09-17-6005-6010-static.jsonl`.
Probe: `../../linux/lightbar/probe-6005.py`.

## Baseline and authorization

Before the test, the user described the lightbar as:

> it's doing the default bios rainbow effect

They authorized the offered 10-second dim-red test with a best-effort off
command afterward, explicitly not restoration of the original effect.

## Execution

The machine log records the actual run on 2026-09-17, from
19:54:40.507668 to 19:54:50.963703 UTC. Device
`0003:048D:6005.0002`, `/dev/hidraw1`, remained bound to `hid-generic`.
The opened device's VID/PID and report descriptor were verified before writes.
All four feature-request ioctl calls returned 8 for an 8-byte buffer.
The red effect request was followed about 10 seconds later by the zero-colour,
zero-brightness sequence. Exact request bytes and timestamps are in the log.

No driver was loaded or rebound. An earlier module-build command was denied
before execution; an earlier attempt to invoke the live probe was blocked by
a permission-checker timeout. Neither is a failed hardware transfer. The log
above is the subsequent successful execution, not output from the mocked tests.

## Human observation after execution

Asked whether the lightbar turned red for about 10 seconds then went dark,
and whether the keyboard changed, the user replied:

> Yes it worked! as you said, lightbar turn red then dark. no change in keyboard.

This is the human observation supporting **physical static red and off control**
using the upstream `6010` static-colour sequence on this `6005` device. It is
stronger evidence than the transfer return values alone. The raw machine log's
`visual_result: pending human report` describes its state when the process
exited; this later observation supplements it without rewriting that log.

## Scope

Confirmed in this run: starting from the reported default rainbow, the lightbar
became red, then dark; the user saw no keyboard change. The requested brightness
was 20/100, not a measured light output. The original rainbow was not restored.

Not established: independent green/blue channels, full brightness scaling,
other effects, LED count/segmentation, persistence across reset or power loss,
suspend/resume, the upstream driver's on/off/timeout commands, or kernel-driver
binding and integration. There was no USB packet capture: the log records
userspace buffers and ioctl returns, not observed on-wire packets.

The source-of-truth EC register statuses are unchanged: this was a USB HID test,
not an experiment on the EC lightbar registers.
