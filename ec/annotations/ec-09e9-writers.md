# `0x09E9` — the two writers, and what `0x0788` carries it to

`ec/annotations/ec-09e9-09eb-sites.md` walked the 9 direct `MOV DPTR` sites of
`0x09E9`-`0x09EB` and left `0x09E9` deliberately without a `registers.yaml` row,
because it has **two** direct writers where `0x09EA`/`0x09EB` have one each.
That file's §6 named that as its own open question. This file is that question,
answered: when each writer runs, whether they can disagree, and what consumes
the byte.

**The short answer.** They can disagree, but only in one cell. Both writers test
the **same** bit — `CTGP_DB_CTRL` (`0x0743`) bit 2 — in **complementary**
senses, so on every state but one they write the same value or only one of them
writes at all. The one cell is `0x0743` bit 2 clear *and* `0x0490` bit 0 set:
there `0x96AD` stores a table byte and `0x9C00` stores zero, and which lands
last is a scheduling question the static image does not answer.

**The byte is not a private scratch register.** `0x83FF` copies `0x09E9` into
`0x0788`, which the DSDT declares as `CTWA`, and ASL `_Q83` reads `CTWA`,
multiplies it by 8, publishes it to `^^^^NPCF.UOCT` and raises
`Notify(NPCF, 0xC0)` — the same NVIDIA platform controller the `0x09EA`/`0x09EB`
chain reaches (§5). So `0x09E9` sits on the GPU cTGP power path, one hop
earlier than the chain
[`ec-09e9-09eb-sites.md`](ec-09e9-09eb-sites.md) §4 draws.

**None of that is a live test.** Every statement here is about instruction
bytes in the committed image, plus the committed DSDT. No register was written,
read back, or observed changing, and `status:` is `present-untested` for that
reason alone. §6 says what the one committed capture does and does not settle,
which is close to nothing.

## 1. The sites, and the anchor convention

The three sites are the `0x09E9` rows of
[`ec-09e9-09eb-sites.csv`](ec-09e9-09eb-sites.csv), regenerated by

```console
$ python3 ec/tools/trace_xdata_refs.py ec/firmware/GMxMGxx_11.800 0x09E9 --csv
```

**A precision point that has to travel with every address in this file.** The
CSV's `runtime` column anchors on the `MOV DPTR,#0x09E9`, and the *access* is the
**next** instruction. So `0x9747` and `0x9C0D` name the two `MOV DPTR`s and the
stores are at `0x974A` and `0x9C10`; the read is `movx a,@dptr` at `0x8428` and
the `xrl a,r7` compare at `0x8429`. Writing "the write at `0x9747`" without
saying which of the two is which is the kind of shorthand that reads as an
error later. `ec/tools/census_xdata_writers.py` reports the same split from the
other end — it names `store_runtime=0x974A` and `store_runtime=0x9C10` for the
two sites whose `runtime` is `0x9747` and `0x9C0D`.

| site (`runtime`) | store/read at | routine | what the value is |
| --- | --- | --- | --- |
| `0x9747` | `0x974A` | `0x96AD` | `[0x0744]`, or `0`, or a CODE table byte |
| `0x9C0D` | `0x9C10` | `0x9C00` | `0x00` |
| `0x8425` | `0x8428` | `0x83FF` | read, compared against `0x0788` |

## 2. Writer one: `0x96AD`, outside the bit-0 gate

`0x96AD` has three `0x0743` tests in the window that matters, and which one
gates the `0x09E9` store is the whole question, so they are separated here.
Decoded from `ec/decompiled/bank0/96AD.asm`, re-run in radare2 (§7):

```
0x96ed  900743   mov  dptr,#0x0743
0x96f0  e0       movx a,@dptr
0x96f1  30e020   jnb  acc.0,0x9714     ; bit 0 clear -> skip BOTH 0x09EA/0x09EB copies
0x96f4  900745   mov  dptr,#0x0745
0x96f7  e0       movx a,@dptr
0x96f8  9009ea   mov  dptr,#0x09ea
0x96fb  f0       movx @dptr,a          ; 0x09EA = [0x0745]
0x96fc  900746   mov  dptr,#0x0746
0x96ff  e0       movx a,@dptr
0x9700  9009eb   mov  dptr,#0x09eb
0x9703  f0       movx @dptr,a          ; 0x09EB = [0x0746]
0x9708  30e104   jnb  acc.1,0x970f     ; bit 1 -> R7 for the 0x94C0 call
0x9711  1294c0   lcall 0x94c0
0x9714  900743   mov  dptr,#0x0743
0x9717  e0       movx a,@dptr
0x9718  30e206   jnb  acc.2,0x9721     ; <== THE GATE for 0x09E9
0x971b  900744   mov  dptr,#0x0744
0x971e  e0       movx a,@dptr
0x971f  8026     sjmp 0x9747           ; bit 2 SET  -> store [0x0744]
0x9721  900490   mov  dptr,#0x0490
0x9724  e0       movx a,@dptr
0x9725  30e01e   jnb  acc.0,0x9746     ; bit 0 clear -> store 0
0x9728  90049f   mov  dptr,#0x049f
0x972b  e0       movx a,@dptr
0x972c  30e10f   jnb  acc.1,0x973e
0x972f  12bb40   lcall 0xbb40          ; fan_mode_get
0x9732  ff       mov  r7,a
0x9733  bf1008   cjne r7,#0x10,0x973e
0x9736  12b984   lcall 0xb984          ; CODE pointer from the 0x0A51 pair
0x9739  7435     mov  a,#0x35
0x973b  93       movc a,@a+dptr
0x973c  8009     sjmp 0x9747           ; store table byte 0x35
0x973e  12b984   lcall 0xb984
0x9741  7434     mov  a,#0x34
0x9743  93       movc a,@a+dptr
0x9744  8001     sjmp 0x9747           ; store table byte 0x34
0x9746  e4       clr  a
0x9747  9009e9   mov  dptr,#0x09e9
0x974a  f0       movx @dptr,a          ; <== the 0x09E9 store
```

**The `0x9747` block is past `0x9714`, so the bit-0 gate at `0x96F1` does not
reach it.** That gate's taken arm is `0x9714`, which is *after* the two
`0x09EA`/`0x09EB` copies and *before* the `0x09E9` one. So the three bytes
`0x96AD` writes on this path are gated differently: `0x09EA` and `0x09EB` need
`0x0743` **bit 0**, and `0x09E9` does not. It runs on every pass that reaches
`0x9714`.

Which is worth stating as its own fact, because it is the difference between
"the `0x09E9` writer is gated" and "the `0x09E9` writer is gated on bit 2":
`0x09E9` has a gate, and it is **bit 2**, not bit 0. Three arms reach the store
at `0x974A`:

- **`0x0743` bit 2 set** → `A` holds `[0x0744]` (`CTGP_OFFSET`), the byte
  `registers.yaml` records as confirmed-working live: with `0x0743=0x03` and
  `0x0744=0x0A` the enforced dGPU limit moved 120 → 130 W on 2026-09-23
  (`CTGP_DB_CTRL / OFFSET`, issue #8). So in this arm `0x09E9` carries the same
  cTGP offset the host writes.
- **`0x0743` bit 2 clear and `0x0490` bit 0 clear** → `0x9746` `clr a`, so
  `0x09E9` is zero.
- **`0x0743` bit 2 clear and `0x0490` bit 0 set** → a CODE table byte read
  through the pointer `0xB984` builds from the `0x0A51`/`0x0A52` pair: byte
  `0x35` when `0x049F` bit 1 is set **and** `fan_mode_get()` returns `0x10`,
  byte `0x34` otherwise.

## 3. Writer two: `0x9C00`, the complement

`ec/decompiled/bank0/9C00.asm`, whole listing, re-run in radare2 (§7):

```
9C00     7f 07 -  mov      R7, #0x7
9C02     12 94 d0 lcall    0x94d0
9C05     90 07 43 mov      DPTR, #0x743
9C08     e0 - -   movx     A, @DPTR
9C09     20 e2 05 jb       0xe2, 0x9c11     ; <== THE GATE, opposite sense
9C0C     e4 - -   clr      A
9C0D     90 09 e9 mov      DPTR, #0x9e9
9C10     f0 - -   movx     @DPTR, A        ; <== the 0x09E9 store
9C11     90 08 ad mov      DPTR, #0x8ad
9C14     e0 - -   movx     A, @DPTR
9C15     20 e0 2f jb       0xe0, 0x9c47
9C18     12 b9 f5 lcall    0xb9f5
9C1B     40 2a -  jc       0x9c47
```

`jb acc.2,0x9c11` skips the store when bit 2 is **set**, and stores `0x00` when
it is **clear**. That is the complement of `0x96AD`'s `jnb acc.2,0x9721` on the
same byte of the same register, read by the same `movx` immediately before each
test. The routine is already named for this in
[`ghidra-functions.csv`](ghidra-functions.csv) —
`clear_09e9_unless_0743_bit2` — and the name is right.

## 4. The reconciliation: one cell, not a race

Putting §2 and §3 side by side, over the two bits that matter:

| `0x0743` bit 2 | `0x0490` bit 0 | `0x96AD` at `0x974A` | `0x9C00` at `0x9C10` | conflict? |
| --- | --- | --- | --- | --- |
| set | either | `[0x0744]` | *skipped* | no — one writer |
| clear | clear | `0x00` | `0x00` | no — same value |
| clear | set | table byte `0x34`/`0x35` | `0x00` | **yes** |

**So the disagreement is a single cell of one byte, and it needs two conditions
open at once.** That is a much weaker claim than "two writers race on
`0x09E9`", and it is the claim the evidence carries: the two stores are on
complementary senses of one bit, so in two of the three rows above they either
do not both run or write the same thing.

**Which one wins the third row is not decided here.** The routines are reached
from unrelated places, so nothing in the image orders them:

- `0x9C00` has exactly **one** entry, the `ljmp 0x9C00` at `0x9B43` inside
  `0x9AAD` (`dispatch_044b_then_write_01_02_03_or_04`), on its `0x044B == 4`
  arm. Two independent readings agree on that: the committed call-target census
  carries `0x09B43` as the only row whose target is `0x9C00`
  ([`bank-call-targets.csv`](bank-call-targets.csv)), and scanning both CODE
  banks for every 8051 branch form that could reach the address — `ljmp`,
  `lcall`, and the fourteen relative-branch opcodes — turns up that one site
  and nothing else. **That is a result about those branch forms.** A computed
  `jmp @a+dptr` off a jump table is invisible to it, as it is to the census, so
  the honest form is "the only *direct* entry this method finds", not "the only
  way in".
- Every entry to `0x96AD` comes from **one** routine, `0x95DD`
  (`fill_08xx_from_code_table`): three `ljmp`s at `0x9611`, `0x9620` and
  `0x9666`, plus the `jz 0x96AD` at `0x96A6` that ends its listing. That is the
  routine the decompiler runs straight through the `0x96AD` function boundary,
  which is why the sibling file's §2 counts `0x09E9` as one write site in two
  `.c` files. The same computed-jump caveat applies.

Nothing connects the two call paths, so "which store lands last" is a
scheduling question about how often each routine runs, and **that is a
different question from which of them is reached from where**. It stays open
here, and it is the same shape of remainder as `ec-09e9-09eb-sites.md` §6's
other items: the control flow is decoded, the timing is not.

**What "two writers" does and does not mean.** It means **two direct
`MOV DPTR,#0x09E9` sites** — `census_xdata_writers.py` names them and reports
the store instruction for each. It does not mean the byte has two writers and no
more. An indirect `movx @Ri`, or a `DPTR` assembled at run time, is invisible to
that scan, and `registers.yaml`'s own caveat says so in as many words. The one
computed-`DPH` site aimed at the `0x09` page is `0x83D6` (`ring_push_0990`),
whose `DPTR` is **bounded to `0x0990`-`0x09BE`** by a decoded counter range
rather than by an empty scan — `ec-09e9-09eb-sites.md` §3 is the argument — so
it cannot reach `0x09E9`. That is a positive exclusion of one idiom, not a proof
that no other writer exists, and it is the same limit the two `0x09EA`/`0x09EB`
rows carry.

## 5. The `0x0788` consumer, and how far it reaches

`0x83FF` (`sync_0788_and_07d4_from_09e9`) is the only **direct** reader of
`0x09E9`, and it reads it to push it somewhere:

```
0x8420  900788   mov  dptr,#0x0788
0x8423  e0       movx a,@dptr
0x8424  ff       mov  r7,a          ; R7 = [0x0788]
0x8425  9009e9   mov  dptr,#0x09e9
0x8428  e0       movx a,@dptr
0x8429  6f       xrl  a,r7
0x842a  600a     jz   0x8436       ; equal -> skip the copy
0x842c  e0       movx a,@dptr
0x842d  900788   mov  dptr,#0x0788
0x8430  f0       movx @dptr,a      ; <== 0x0788 = [0x09E9]
0x8431  7d83     mov  r5,#0x83
0x8433  12163c   lcall 0x163c      ; raise the 0x83 notify
```

So `0x09E9` → `0x0788`, conditional on the two differing, and each time it
differs the routine raises notify code `0x83`. That is the last of the EC's own
work on this byte; everything past `0x0788` is ASL.

**`0x0788` is `CTWA`, and `_Q83` is the consumer.** From
`evidence/acpi/dsdt.dsl`, the ECMG field list declares it —
`Offset (0x788), CTWA, 8` (:52221-52222) — and the `_Q83` query method reads
it (:52783-52791):

```
Method (_Q83, 0, NotSerialized)
{
    IO80 = 0x83
    Local0 = Zero
    Local0 = CTWA                              ; dsdt.dsl:52787
    Local0 = (Local0 * 0x08)
    ^^^^NPCF.UOCT = Local0                     ; dsdt.dsl:52789
    Notify (NPCF, 0xC0)                        ; dsdt.dsl:52790
}
```

`^^^^NPCF.UOCT` is the NVIDIA platform controller's cTGP **offset** field, and
the `* 0x08` scale factor is the same one `_Q84` applies to `CPUA`/`DBAP`
(:52801-52802). `NPCF` is the AML-created device node at
ToUUID `36b49710-2483-11e7-9598-0800200c9a66` (dsdt.dsl:52772,
:52780) that
`ec-09e9-09eb-sites.md` §4 already draws the end of.

**The ASL also writes `CTWA`, and that is the more useful half of this.** `T1WR`'s
`Arg0 == 0x1171` arm (dsdt.dsl:50658-50666) stores `Arg1` into `CTWA`,
multiplies by 8 and publishes `UOCT` and notifies — the same three steps `_Q83`
performs, in the same order. So `CTWA` is both a host-writable register and an
EC-written one.

**And it is the only ECMG field the ASL both writes and reads.** That is a
sweep over the committed field list rather than an impression from reading
`_Q83`: taking each row of
[`dsdt-ecmg-fields.csv`](dsdt-ecmg-fields.csv) that carries `asl_sites`, and
deciding each of those lines *write or read* by whether the field name is the
left-hand side of an assignment (an `==` is a comparison, not an assignment),
`CTWA` at `0x0788` is the only field whose sites resolve both ways. The rest are
write-only from ASL — the `APL*` and `APTC`/`APTN` power-limit bytes, `CGCT`,
`DBD1`/`DBD2`, and the `MGI*`/`CCI*` bank — or read-only: `DBEN`, `GFID`,
`PDIN`, `WHMS`, `CPUA`, `DBAP`.

The bound on that is the sweep's own: it records the ECMG field list's
references **as found by its search**, so a field reached by a route it does not
enumerate would not appear. What it supports is that `0x0788` is a meeting point
rather than a pass-through — the same byte is written from both sides of the
EC/ACPI boundary — which is the part this file rests on.

**Where the reading stops.** Whether ASL `_Q83`'s `IO80 = 0x83` and the EC's
`R5 = 0x83` push through `0x163C` are **one protocol** or two things that share
a number is a reading of the shape, not a claim. `0x163C` is a one-instruction
stub — `mov dptr,#0x88f0 ; ljmp 0x1114` — in a contiguous run of such stubs
`0x163C`-`0x1672` that all push a DPTR and a code `0x11` onto the stack;
[`a73f-notify-path.md`](../../docs/findings/a73f-notify-path.md) records the ring
they feed. Nothing decoded here shows the host's `_Q83` and the EC's `0x83`
crossing, and they are named here as the same **number** on two sides, nothing
more.

**And what reaches the copy is narrower than it looks.** `0x83FF` has exactly
one direct call site, `lcall 0x83ff` at `0x8551`, and that address sits in the
run of bare `lcall`/`ljmp` stubs between `0x851B` and `0x8557` that no exported
function covers — the same unresolved run
[`ec-09e9-09eb-sites.md`](ec-09e9-09eb-sites.md) §6 names when it records that
`0x83FF`'s caller is not identified. So **the routine that propagates `0x09E9`
to `0x0788` is called from a place this repository has not resolved**, which is
the concrete reason §4's "which writer lands last" cannot be answered by
reading a caller chain: the chain from the `0x09E9` writers to the `0x0788` copy
is broken at its far end.

The other way in does not carry the copy either. `0x8044` is a single
`ajmp 0x845d` into the middle of `0x83FF` — already recorded as a forwarder in
[`ghidra-functions.csv`](ghidra-functions.csv) — and `0x845D` is past the
`0x8420`-`0x8433` block, so a caller arriving that way reaches the `0x09EA`/
`0x09EB` half and never touches `0x0788`. The `0x09E9` → `0x0788` hop is on the
`0x8551` path alone.

## 6. What the 2026-09-23 capture does and does not establish

`evidence/ec-watch/2026-09-23-power-mode-cycle-0700-07ff.csv` is the one
committed capture in which the gate this chain runs behind was opened. It is
also **the wrong shape for this byte**, and the reason is in the filename: it
watched `0x0700`-`0x07FF`. Every address it carries is in that range, `0x09E9`
and `0x0788` among the ones it does not, and it does carry `0x0743` — so it
saw the gate open and nothing downstream of it.

**So: a weak negative, and it changes nothing.** The file has no `0x09E9` row
and no `0x0788` row. That is "this capture did not observe the byte", which is
a statement about the capture's watch window, **not** a statement about whether
the writers ran. A byte that did not move is not evidence the EC does not act on
it — it is evidence that nothing this capture watched wrote it.

**What it does establish is upstream and already established.** Its `0x0743`
rows (`0x00 -> 0x02` at `17:57:41.307`, `0x02 -> 0x03` at `17:57:51.589`) are
the transitions `ec-09e9-09eb-sites.md` §5 works over, and they are read there.
This file adds nothing to them.

**The run that would speak, and why the prepared one cannot.** Watching
`0x09E9` and `0x0788` next to `0x0743` is a human step at the physical machine
(CLAUDE.md, "Cloud agents cannot reach the hardware");
[`gpu-tgp-07c4-07d7-door.md`](../../docs/hardware-tests/gpu-tgp-07c4-07d7-door.md)
is the prepared procedure and **as written it cannot do this** — its `WATCH`
set covers `0x07C4`-`0x07D7` and `0x0743`-`0x0746` and no `0x09xx` or `0x0788`
address. Extending that set would break the deliberate 24-address contract
`windows/tools/test_gpu_block_watch.py` pins, and that is #94's to own. The
door's status stays **not run** and nothing under `evidence/` comes from it.

## 7. Spot-checks against an independent disassembler

Every listing this file's argument rests on was re-run in radare2, the house
method for this (`ec-09e9-09eb-sites.md` §7,
[`manual-fan-ctrl-0751.md`](manual-fan-ctrl-0751.md) §7;
`ec/tools/disasm8051.py` is the fallback, not the authority):

```console
$ python3 ec/tools/make_bank_image.py ec/firmware/GMxMGxx_11.800 0 0x08000 /tmp/bank0.bin
$ r2 -a 8051 -e scr.color=0 -q -c 's 0x96ed; pd 47' /tmp/bank0.bin   # 2: three gates, to the store at 0x974A
$ r2 -a 8051 -e scr.color=0 -q -c 's 0x9c00; pd 9'  /tmp/bank0.bin   # 3: the jb and the store at 0x9C10
$ r2 -a 8051 -e scr.color=0 -q -c 's 0x8420; pd 12' /tmp/bank0.bin   # 5: the read, compare and copy
$ r2 -a 8051 -e scr.color=0 -q -c 's 0x9b30; pd 12' /tmp/bank0.bin   # 4: the ljmp at 0x9B43
```

The `pd` counts are the ones that actually reach the address each comment names;
a shorter window stops before it and would silently verify less than the comment
claims. All four matched the committed `.asm` instruction for instruction. The
"complementary on one bit" claim is also pinned mechanically, by bytes rather
than by prose: the `0x96AD` window carries `30 e2` (`jnb` bit 2) ahead of its
`90 09 e9`, the `0x9C00` window carries `20 e2` (`jb` bit 2) ahead of its own
`90 09 e9`, and `ec/tools/test_xdata_09e9_two_writers.py` asserts both.

## 8. Calibration

- **A store is not a behaviour.** `0x09E9` → `0x0788` is an instruction that
  copies a byte, and `0x0788` → `UOCT` is ASL reading a field. Neither is
  evidence that the EC or the platform controller *acts* on the value. What
  would be: a live run watching `0x09E9`, `0x0788` and `0x0743` together, which
  §6 says is a human step.
- **"Two writers" is a statement about a method**, per §4 — two direct
  `MOV DPTR` sites, with the `0x0990`-`0x09BE` bound excluding the one computed
  `DPH` on this page, and indirect forms still outside it.
- **`present-untested` is the ceiling and it stays.** No hardware was involved
  in any of this, and nothing here moves `0x09E9` or `0x0788` off it.
- **The open remainder is named, not filled in.** Which of the two stores wins
  the §4 conflict cell depends on how often each routine runs; the timing is not
  in the image.
