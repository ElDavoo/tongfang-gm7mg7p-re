# `0x0400-0x045F`: the EC side of the battery/temperature page

Issue #148 asked which of the 96 bytes `windows/tools/manual_fan_ctrl_probe.py`
and `docs/hardware-tests/manual-fan-ctrl-0751-isolation.md` §3 read twice per
block the EC firmware actually touches, in which image, doing what, and from
which routine. This is the answer. The machine-readable table behind every
number here is **`xdata-0400-045f-sites.csv`**, the `--csv` output of
`ec/tools/trace_xdata_refs.py` over all 96 addresses; §7 carries the check
that re-derives `registers.yaml`'s counts from it.

Nothing in this file is a live observation. Every status it supports is
`present-untested` except the two entries that rest on already-cited
2026-09-17/18 cross-checks, and those cross-checks are cited rather than
repeated.

## 1. How to reproduce it

```console
$ cd ec/tools
$ python3 make_bank_image.py ../firmware/GMxMGxx_11.800 1 0x10000 /tmp/bank1.bin
$ python3 make_bank_image.py ../firmware/GMxMGxx_11.800 0 0x08000 /tmp/bank0.bin
$ python3 trace_xdata_refs.py ../firmware/GMxMGxx_11.800 \
        $(python3 -c "print(' '.join(f'0x{0x400+i:04X}' for i in range(0x60)))") \
        --csv > ../../ec/annotations/xdata-0400-045f-sites.csv
```

That is the whole sweep, and it is read-only: `trace_xdata_refs.py` opens the
image, does no writes, and needs no hardware. `check_register_counts.py` and
`register_ref_table.py` then check the result against `registers.yaml` (§7).

## 2. The blind spot, which travels with every number

`trace_xdata_refs.py` finds **direct** `MOV DPTR,#addr` sites and nothing else.
A byte reached through a computed DPTR, a register-indirect XDATA access, or a
table lookup is invisible to it. So:

- a **zero** anywhere in this file means *not found by this method*. It is
  never evidence a byte is unused, and no entry here is `absent`;
- a **table lookup** really does hide a writer, and not only in principle:
  `0x0440` is written by three three-byte CODE records reached through
  `code_table_scatter_to_xdata` (bank1 `0xA530`) and has no `MOV DPTR` site at
  all, so its 43-reader / 0-writer row below is wrong about the writer and right
  about the readers. See `xdata-0440-readers.md`;
- a **write** means the instruction stores to the byte. It is not evidence the
  EC acts on the value, and nothing here is `confirmed-*` on the strength of
  one;
- the access column is a **linear 8-instruction walk**, not a disassembler
  (`ec/README.md`, and the tool's own docstring). `handoff` means DPTR went to
  a subroutine and the direction was not settled at the site; §4 settles it one
  level down.

This is the same caveat `docs/findings.md` §4c and the 0x07B9 retraction in
`registers.yaml` carry, and it is why no entry on this page is `absent` and
why the 50 bytes in §6 are described rather than entered.

## 3. What the sweep found

**46 of the 96 bytes have at least one EC-side direct site: 309 sites**, 233 in
`bank1`, 73 in `bank0`, 3 in the common area. A further 100 sites on the same
page are in the `ITE8850-PD` image at file `0x20000`, which is a separate 8051
program with its own XDATA map (`ec/README.md`, `lightbar-bat-flow.md` §2) —
**not EC references**, and §6 is where they show up. File-wide the page has 409
sites.

By access, the 309 EC-side sites are:

| | count | what it means |
|---|---:|---|
| direct read | 173 | `movx a,@dptr` at the site |
| direct write | 48 | `movx @dptr,a` at the site |
| direct read-modify-write | 20 | read, mask/or, store back at the site |
| DPTR handoff | 63 | direction not settled at the site; §4 resolves it |
| no `movx` in the window | 5 | the walk stopped on something else |

That is 309. The busiest bytes are `0x0440` (43, every one a read), `0x045A`
(22), `0x0436` (17), `0x043E` (15, already entered), `0x0438` (14), `0x044F`
(14, already entered) and `0x0456` (12). `0x0440` is worked through in
**`xdata-0440-readers.md`**: it does have a writer, reached through a
three-byte CODE record rather than a `MOV DPTR` site, which is the second
blind spot this sweep's counts cannot show. **30 bytes have an EC-side write**, and
all 20 of the page's read-modify-writes sit in seven of them, between `0x0442`
and `0x045B` — the flag block, where a byte is assembled a bit at a time
instead of stored whole. The derived bytes inside that span are a different
thing: `0x0448`, `0x0449` and `0x0450`-`0x0455` have writers that store a
computed value (a scaled quotient, a copied byte), not a bit.

**286 of the 309 EC-side sites (93%) sit inside a function this repo has
already exported and named** in `ec/decompiled/` — matched by runtime address
against `ec/decompiled/listing-index.csv`. This was a reading exercise over code
the repository has decompiled, not a disassembly project. The 23 that do not are
in the gaps between exports; §5 names them by address.

## 4. The 63 handoffs, resolved one level down

`ec/tools/register_ref_table.py --callee-depth 1` resolves a handoff by
decoding the callee. For this page every EC-side handoff goes to one of six
routines, and five of the six are named and hand-decoded in
`ec/decompiled/bank1/8886..889E.c` and `ec/decompiled/bank0/E3C4.c`:

| callee | what it is | handoffs | resolves to |
|---|---|---:|---|
| `0x8886` `read_xdata_pair_to_r1r2` | reads two adjacent XDATA bytes into R1:R2 | 20 | read |
| `0x8892` `read_xdata_pair_to_r3r4` | the same into R3:R4 | 15 | read |
| `0x888C` `write_r1r2_to_xdata_pair` | stores R1:R2 out, low byte first | 19 | write |
| `0x889E` `write_r3r4_to_xdata_pair` | the same from R3:R4 | 6 | write |
| `0xE3C4` `set_r6_from_a_r7_from_dptr` | 5 bytes, one of them a `movx` read | 2 | read |
| `0x8863` `FUN_CODE_8863` | **unnamed**, 23 bytes, boundary a hypothesis | 1 | unresolved |

**37 resolve to a read, 25 to a write, 1 stays unresolved.** So of the 309
EC-side sites, 210 are reads (173 direct + 37), 73 are writes (48 + 25), 20 are
read-modify-writes and 6 are unresolved — which is 309 again. The 15 handoffs
into `0x0436` alone resolve 8 read / 7 write, which is the clearest single
statement about that byte: **the EC reads and writes `0x0436` as one 16-bit
value**, and the width comes from the helpers rather than from a guess.

The one unresolved handoff is `0x0400` at bank1 `0xBF42`, which passes DPTR in
R3:R4 along with R5:R6 to an unnamed routine this repo has not annotated. Its
direction is not established here.

seeding still wants a project rebuild.

## 6. The 50 bytes deliberately not entered

A byte is entered in `registers.yaml` **if and only if** the EC image has at
least one direct `MOV DPTR,#addr` site for it. That is 46 bytes, 44 of them
new — the other two are `CPU_TEMP` (`0x043E`) and `GPU_TEMP` (`0x044F`), which
were already there. The 44 new ones are carried as **39 entries** and, with the
two pre-existing, **41 entries cover 46 bytes**, the difference being the five
entered as 16-bit pairs. Entering the remaining 50 would put 50 rows in the
YAML whose entire content is a zero, or a PD-image count, and a zero here means
"not found by this method" — a row saying nothing while looking like a finding.

**39 bytes have no site in any image.** `0x0405` `0x0406` `0x0407` `0x0409`
`0x040B` `0x040D` `0x040F` `0x0411`-`0x0417` `0x0419`-`0x041B` `0x041D`-`0x041F`
`0x0421`-`0x0423` `0x0425` `0x0427` `0x042B` `0x042D` `0x042E` `0x0430` `0x0431`
`0x0441` `0x0444`-`0x0447` `0x044A` `0x044D` `0x044E` `0x0453`

**11 more have sites only in the PD image**, 50 of the page's 100 PD sites —
a byte whose file-wide count is entirely another program's XDATA, which is the
0x07E2-0x07E5 situation `lightbar-bat-flow.md` §6 is about, and the reason a
bare count is not an EC finding:

| byte | PD sites | byte | PD sites | byte | PD sites |
|---|---:|---|---:|---|---:|
| `0x0418` | 5 | `0x0426` | 1 | `0x042A` | 2 |
| `0x041C` | 3 | `0x0428` | 3 | `0x042C` | 6 |
| `0x0424` | 12 | `0x0429` | 2 | `0x042F` | 9 |
| `0x0433` | 5 | `0x043B` | 2 | | |

Three of these are the *high halves* of a 16-bit value whose low half is
entered — `0x0405` with `0x0404`, `0x0409` with `0x0408`, `0x0433` with
`0x0432` — so the pair is entered from its low half only, and the entry says
which half it is. `0x0433` having 5 PD sites and no EC site is the clearest
example on the page of why the image split is not optional.

**No byte on this page is `unknown-not-absent`.** That status means a live
observation exists with no EC-side site behind it, and none was found: §8 lists
every byte that moved in the one committed capture covering this page, and all
of them have EC-side sites.

## 7. The per-address table

EC/PD split and the `b1`/`b0`/`c` columns (bank1 / bank0 / common area) are
site counts; the access columns classify the EC-side sites only; the last
column names the routines holding the writing sites. `*(not entered)*` marks a
byte in §6. Every cell is re-derivable from `xdata-0400-045f-sites.csv`, and
this is the check that keeps the YAML and the table from disagreeing:

```console
$ python3 - <<'EOF'
import csv, collections, yaml
tot, ec, pd = collections.Counter(), collections.Counter(), collections.Counter()
for r in csv.DictReader(open('ec/annotations/xdata-0400-045f-sites.csv')):
    a = int(r['addr'], 16); tot[a] += 1
    if r['region'] in ('common', 'bank0', 'bank1'): ec[a] += 1
    elif r['region'] == 'pd-image': pd[a] += 1
bad = 0
for e in yaml.safe_load(open('ec/annotations/registers.yaml'))['registers']:
    addrs = e['addr'] if isinstance(e['addr'], list) else [e['addr']]
    for key, table in (('static_refs', tot), ('static_refs_main_ec', ec),
                       ('static_refs_pd_image', pd)):
        got = e[key] if isinstance(e[key], list) else [e[key]] * len(addrs)
        for addr, recorded in zip(addrs, got):
            if not 0x400 <= addr <= 0x45F: continue
            if recorded != table[addr]: print('MISMATCH', e['name'], hex(addr)); bad += 1
print('mismatches:', bad)
EOF
mismatches: 0
```

That is `check_register_counts.py` re-derived from the committed CSV instead of
from the image — 138 page count keys, 0 mismatches. The tool itself
(`check_register_counts.py ec/firmware/GMxMGxx_11.800`, run by
`.github/scripts/agent-gates.sh`) is the same check against the image, and
`register_ref_table.py ec/firmware/GMxMGxx_11.800 --callee-depth 1` is the
stronger one: it is driven by `registers.yaml`, so these 46 addresses are the
first on the page to be reconciled whole, and it exits non-zero unless every
class bucket sums to the address's site count and main + PD to the file-wide
total.

## 8. Reconciliation with the one committed capture

`evidence/ec-watch/2026-09-18-profile-switch-0400-07ff.csv` is the only
committed capture that covers this page. It watched `0x0400-0x07FF` at 0.3 s
while the vendor service cycled the three battery modes, and recorded 4960 byte
changes, **674 of them on `0x0400-0x045F`**. Six bytes on this page moved:

| byte | changes | what it did |
|---|---:|---|
| `0x044C` | 247 | sensor-scale jitter, both directions |
| `0x0449` | 238 | sensor-scale jitter, both directions |
| `0x043E` | 180 | `CPU_TEMP`, 0x39-0x5A |
| `0x0436` | 4 | `0x70 → 0x84 → 0x98 → 0xAC → 0xC0` — exactly `+0x14` every ~35 s, at 23:03:21, 23:03:56, 23:04:30, 23:05:05 |
| `0x044F` | 4 | `GPU_TEMP`, ±1 |
| `0x0438` | 1 | `0x97 → 0xAE` once, at 23:03:49 |

**Every one of the six has EC-side direct sites**, so there is no 0x07B9-shaped
case on this page — no byte here moved with no firmware reference behind it.
That is a result, not an absence of one.

**`0x0436` is the interesting row, and it is why that pair is left unnamed.**
Upstream `uniwill-laptop` calls `0x0436`/`0x0437`
`EC_ADDR_BAT_REMAIN_CAPACITY` (`uniwill-acpi.c:79,81`), and it is the only
name anyone has for the address. But this capture does not read like a
capacity field: the low byte steps by exactly 20 every 35 seconds with no
scatter, and the high byte never moves at all. A perfectly periodic ramp is a
counter; a remaining-capacity reading moves with load. `docs/findings.md` §4g
groups `0x0436` with `0x0438` as "voltage", and that is wrong in the other
direction too — `0x0438` moved exactly once here, and its reading as terminal
voltage in mV is separately established three ways (§9). The correction is
recorded next to the §4g claim rather than folded into it.

So `0x0436`/`0x0437` is entered as `XDATA_0436_PAIR` with the upstream name
recorded but not adopted, and the note in `registers.yaml` says why. **A live
read of `0x0436`/`0x0437` beside WMI's `RemainingCapacity` is the experiment
that would settle it** — a human at the machine, and the obvious next issue
this sweep opens. Issue #172 is that issue, and the experiment is now written
down rather than only described: `windows/tools/ec_validate.py` samples the
pair at 1 s beside WMI's `RemainingCapacity` under §4g's rule,
`linux/battery-trace/remain-capacity-probe` is the read-only Linux equivalent
against `charge_now` and `capacity`, and
`docs/hardware-tests/remain-capacity-0436.md` is the step-by-step. **None of
them has been run**, so the question §11 item 1 carries is still open and the
placeholder stands.

## 9. Names: where each one comes from

Nothing here is named from memory. There are three provenance classes, and
every entry's `sources:` says which it is.

**Quoted from upstream, at a pinned ref.** `Wer-Wolf/uniwill-laptop` commit
`5a24248f6422a0b673a47cbfd65e19a98eb4c8a9` (branch `master`), file
`uniwill-acpi.c`. The page is upstream's smart-battery block, laid out
consecutively:

```c
#define EC_ADDR_BAT_POWER_UNIT_1        0x0400   // :54
#define EC_ADDR_BAT_DESIGN_CAPACITY_1   0x0402   // :58
#define EC_ADDR_BAT_FULL_CAPACITY_1     0x0404   // :62
#define EC_ADDR_BAT_DESIGN_VOLTAGE_1    0x0408   // :66
#define EC_ADDR_BAT_STATUS_1            0x0432   // :70
#define BAT_DISCHARGING                 BIT(0)   // :71
#define EC_ADDR_BAT_CURRENT_1           0x0434   // :75
#define EC_ADDR_BAT_REMAIN_CAPACITY_1   0x0436   // :79
#define EC_ADDR_BAT_VOLTAGE_1           0x0438   // :83
#define EC_ADDR_SYSTEM_ID               0x0456   // :91
#define HAS_GPU                         BIT(7)   // :92
```

Nothing from that file is committed here; a `file:line` at a pinned SHA is what
`sources: [uniwill-laptop, ...]` has always meant in this repo. Where upstream
pairs a byte with a neighbour that has no EC-side site (`0x0405`, `0x0409`,
`0x0433`) only the low half is entered, and the entry says so — which is why
`BAT_FULL_CAPACITY_1`, `BAT_DESIGN_VOLTAGE_1` and `BAT_STATUS_1` carry
upstream's `_1` suffix on their own.

**`0x0456` is the one the issue asked about, and upstream does name it.**
`EC_ADDR_SYSTEM_ID` is read at `uniwill-acpi.c:2820` to test `HAS_GPU` (bit 7)
before the driver exposes GPU_TEMP and NVIDIA_CTGP_CONTROL, so the name is
cited, not recalled. The EC image is consistent with a capability byte: 9 of
its 12 sites are direct reads and nine of *those* are bit tests — bit 7 at
bank0 `0x8C69`, `0x93F4` and `0xC26E`, bit 6 at bank1 `0xF3C9`, bit 5 at bank0
`0xB38E` and behind an `anl a,#0xe0` at bank1 `0x83E5` — while the three
writers assemble it, clearing bits 4-5 at bank0 `0xAD65` and setting bit 6 then
bit 7 at bank0 `0xDA81`. Both writers are confirmed against `r2` (§10). Bits
0-3 are never touched by any site found here. **That is a shape, and a shape
is not a name**: the entry is `present-untested`, the bit layout is upstream's,
and bit 7 being `HAS_GPU` on this board is a plausible reading of a consistent
shape, nothing more. One of its bits is load-bearing — `0xF3C9` picks its
divisor `0x22` or `0x44` from bit 6 before scaling `0x060C`/`0x060D` into
`0x0449` — which is a testable claim the next hardware run could settle.

`ec/tools/ecmem.py`'s record that `0x456` reads were cross-checked against the
`uniwill-laptop` regmap debugfs dump before the first write is **not**
`live` evidence and is not recorded as such: two software paths agreeing on a
read is not a behavioural test, and the entry's `sources:` does not list
`live`.

**Corroborated by this repo's own committed traces**, independent of upstream:
`0x0434`/`0x0435` is battery current in mA (2040 mA against `0x0438`'s 16021 mV
= 32.68 W, against the ACPI driver's own 32.683 W — `docs/findings.md` §4g) and
`0x0438`/`0x0439` is terminal voltage in mV (the 10/10 exact-copy match in
`ec_validate.py`, plus `charge_target_update` and the pair reader). Upstream
agrees with both, which is a third and fourth source, not the only one — which
is why these two can be `live` and the rest cannot.

One citation note, since it is easy to trip over: that validation passage is
in `findings.md` §4g, not §4d. The older `CHARGE_TARGET_MV` note above cites
§4d for the same 10/10 match; that reference is left as it is rather than
edited from here, and it is wrong in the same way — §4d is the static-scan
validation, which is a different argument.

**The other 32 bytes are entered as `XDATA_04XX`.** The page is a mix of
temperatures, voltages, derived scaled values and flag bytes, and a guessed name
in a symbol table is the cheapest-looking overclaim available: it reads as
knowledge in every decompile that mentions the byte, and `ec-0x07d0-sites.md` §5
is the worked example of what a `MOV DPTR` site turns out to be when the code
around it is actually read. `XDATA_04XX` is greppable, unique, and claims
nothing. Several of these bytes are nonetheless well understood *structurally* —
`0x0448` is the battery voltage divided by 100, `0x0449` the battery current
divided by 100, `0x0443` a counter gated on `0x0440`, `0x045B` bit 0 a flag
with four named owners — and that goes in the note rather than the symbol.

## 10. Cross-decoder spot checks

`trace_xdata_refs.py`'s docstring asks for anything load-bearing to be
confirmed against a second decoder, because the walk it does is linear and can
misframe. The four that carry weight here, with `make_bank_image.py` images
and `r2 -a 8051`:

```console
$ r2 -a 8051 -e scr.color=0 -q -c 's 0xad65; pd 4' /tmp/bank0.bin

0x0000ad68  e0       movx a, @dptr
0x0000ad69  54cf     anl a, #0xcf
0x0000ad6b  f0       movx @dptr, a

$ r2 -a 8051 -e scr.color=0 -q -c 's 0xda81; pd 8' /tmp/bank0.bin
0x0000da81  900456   mov dptr, #0x0456
0x0000da84  e0       movx a, @dptr
0x0000da85  4440     orl a, #0x40
0x0000da87  f0       movx @dptr, a
0x0000da88  e0       movx a, @dptr
0x0000da89  4480     orl a, #0x80
0x0000da8b  f0       movx @dptr, a

$ r2 -a 8051 -e scr.color=0 -q -c 's 0xb8b9; pd 14' /tmp/bank1.bin
0x0000b8b9  900575   mov dptr, #0x0575
0x0000b8bc  e0       movx a, @dptr

0x0000b160  e0       movx a, @dptr
```

All four agree with the walk. The last is `charge_target_update` reading the
voltage pair high byte first into R4, low byte into A, then `lcall 0xBB90`
(`store_be16_a`) to copy it to `0x0A48` — which is the third of the three
independent sources for `0x0438` being the pack's terminal voltage, and a
concrete reason the symbol is `BAT_VOLTAGE_MV_0`/`_1` by address order and not
`_HI`/`_LO`: the generator's docstring is right that an endianness claim baked
into a symbol outlives the note that would have to correct it.

### 10a. `0x0403`'s threshold constant, checked the same way

`registers.yaml`'s `BAT_DESIGN_CAPACITY` note says 10 of `0x0403`'s 11 direct
reads subtract `0x14` from the byte. The issue that opened §8's question (#172)
said 11, so it is worth the second decoder, and `trace_xdata_refs.py` plus `r2`
agree on 10 — the eleventh, bank1 `0xA269`, is a plain `jz`:

```console
$ r2 -a 8051 -e scr.color=0 -q -c 's 0x9310; pd 4' /tmp/bank1.bin
0x00009310  900403   mov dptr, #0x0403
0x00009313  e0       movx a, @dptr
0x00009314  c3       clr  c
0x00009315  9414     subb a, #0x14

$ r2 -a 8051 -e scr.color=0 -q -c 's 0xa269; pd 3' /tmp/bank1.bin
0x0000a269  900403   mov dptr, #0x0403
0x0000a26c  e0       movx a, @dptr
0x0000a26d  606b     jz 0xa2da
```

**The one observation this produces, and it is a question rather than a
finding.** That `0x14` is the same `0x14` as the step `0x0436` takes in §8's
committed capture: two addresses on this page, inside the block upstream lays
out as the smart-battery one, both using the constant twenty. It could be a
coincidence — twenty is a small number and a small number is an easy thing to
reach for twice — or it could be one quantity compared against one field.
**Nothing here says which, and this check does not connect the two.** It is
recorded because it is worth noticing while the page is mapped, and because
issue #172's two readings of `0x0436` are exactly the readings this constant
would have to arbitrate.

Two things it explicitly is **not**. It is not evidence that `0x14` is a unit
for `0x0402`/`0x0403` — a threshold comparison against a 16-bit field does not
establish what the field is measured in, and `BAT_DESIGN_CAPACITY` remains
`present-untested` with no unit of its own. And it is not a second reading of
`0x0436`: `0x0436` is a different address, the constant is compiled into
`0x0403`'s comparison, and neither tells us what moved `0x0436` in the
capture.

## 11. What this changes, and what it leaves stale

- **39 new entries, 44 new addresses** in `ec/annotations/registers.yaml`, all
  `present-untested`, plus the `xdata-refs` source tag in its header. No
  existing entry's status moves.
- **`ec/ghidra/xdata-overrides.csv` gains 10 rows**, one per address of the
  five two-byte entries: a two-address entry whose name does not split 1:1 on
  `" / "` will not name itself, so the `_0`/`_1` pairs are hand-named there,
  each `reason` citing where the name comes from. `0x0456` needs no override —
  `SYSTEM_ID` is a single-address entry with a usable C identifier, so the
  generator's rule 1 names it.
- **`ec/ghidra/xdata-symbols.csv` is regenerated**, 56 rows to 101, by
  `ec/tools/gen_xdata_symbols.py` — never by hand. `ghidra tooling` in
  `.github/scripts/agent-gates.sh` is what proves the committed CSV is a fresh
  generation rather than an edit.
- **The new symbols reach the Ghidra project at the next build.**
  `build_ec_decompile.py --check` verifies listing bytes and the export
  manifest, not symbol names, so the `.c` files under `ec/decompiled/` are
  *not* stale in any way the check can see — but they still read
  `DAT_EXTMEM_0438` rather than `BAT_VOLTAGE_MV_0` until that build runs. No
  rebuild is in this change and none is needed.
- **Fifteen plate comments had gone stale on this page, and are fixed in
  `ec/annotations/ghidra-functions.csv`.** "X has no entry in
  `ec/annotations/registers.yaml`" is a house idiom used across this tree, and
  entering these bytes made it false wherever it named one of them. Fifteen
  comments were affected: the seven listed here when the page was swept, and
  eight more that the check below turned up once it existed — `bank0/9A0E.c`
  (`0x044B`), `bank0/909B.c` (`0x045B`), `bank0/9A9C.c` and `bank0/BD20.c`
  (both `0x044B`), `bank0/BC71.c` (`0x0434`/`0x0435`), `bank0/9CA6.c`
  (`0x0440`, `0x0442`), `bank0/BF12.c` (`0x043D`) and `bank1/80EF.c`
  (`0x0440`) — twenty stale claims in all. Each was reworded to say what the
  entry now says, and the addresses named beside them that genuinely have no
  entry — `0x060C`, `0x08EA`, `0x08E2`, `0x0460`, `0x0468`, `0x06C5` among
  them — keep saying so. A true "no entry" claim is a finding, and dropping one
  to tidy a sentence would trade one overclaim for another.
  **The generated `.c` files still carry the old wording, and no re-export is in
  this change.** That is not an oversight: `export-only` copies the project and
  runs `ApplyAnnotations.java` over the copy with *both* the annotations and
  `ec/ghidra/xdata-symbols.csv`, so a re-export also renames every XDATA symbol
  that file names. It was regenerated by this page's sweep (101 symbols, all
  current — `ec/tools/gen_xdata_symbols.py --check`) *after* the last export,
  so 190 `.c` files now differ from what a build produces, and every one of
  them differs in C rather than in prose. Committing a prose correction with
  190 files of renames attached would bury it, and the renames are the
  seeding issue's work — see the bullet above. The fix is in the CSV, which is
  where the prose lives; the next export that is *meant* to carry the renames
  carries these fifteen comments with it.
- **The class is checked now, not just corrected.**
  `build_ec_decompile.py --self-test` fails when an annotation comment claims
  the YAML holds no entry for an address it has since gained one. It resolves
  the addresses each "no entry" clause actually governs — the subject of the
  clause, or, for the two forms whose subject is a pronoun, the addresses named
  earlier in the comment — so the true claims above survive it; and it names
  the address in the failure, so a false positive can be told from a real one
  without re-deriving the scan. The check's own docstring carries the five
  forms of the idiom and how each resolves. A claim it cannot enumerate is
  left alone rather than widened to a guess: `bank0/96AD.c`'s "none of the
  0x08xx or 0x09xx destinations has an entry" is one, and it is true — no
  address in either range has an entry — so it stays.
- **Open questions this sweep raised**, for the follow-up pass:
  1. `0x0436`/`0x0437` — is it a counter, or upstream's remaining capacity?
     Needs one live read beside WMI `RemainingCapacity`. **The highest-value
     follow-up on the page.** Issue #172 wrote the two probes and the procedure
     for it (`docs/hardware-tests/remain-capacity-0436.md`); the run is a human's
     and has not happened.
  2. `0x0440` — 43 read sites and no writer, and the page's busiest byte. What
     do 43 places in the firmware consult it for? **Answered** in
     `xdata-0440-readers.md`, with the per-site table in
     `xdata-0440-readers.csv`: the readers group by constant *and* consequence,
     the compared set is {0, 5, 6, 7, 8} with 39 of the 43 accepting any
     non-zero byte, 16 of the 43 are co-gated on `0x06E6 == 0x01`, and the
     writer is a three-byte CODE record through `code_table_scatter_to_xdata`
     (bank1 `0xA530`) rather than a `MOV DPTR` site — three records, all
     storing `0x00`. The status stays `present-untested`; nothing there is a
     readback.
  3. `0x0456` bits 4-7 — upstream says bit 7 is `HAS_GPU`; bit 6 demonstrably
     selects a divisor for `0x0449`. A live read of the byte beside a GPU/dGPU
     state change would settle both.
  4. `0x0457` — four read-modify-writes and no enclosing export (§5). Seeding
     that routine needs a project rebuild.
  5. The 11 PD-only bytes in §6, and the 39 with no site in any image: neither
     group is `absent`, and both would move off "not found by this method" the
     moment something looks for them indirectly.
