# What `functions_touched` counts (issue #1360)

`ec/annotations/xdata-registers.csv` carries `functions_touched`, `readers` and
`writers` per address, and nothing on the row or in
`ec/tools/xdata_register_map.py` said what they counted. This is the ruling, and
the tool that makes the other reading derivable instead of asserted:

```
python3 ec/tools/xdata_frame_credit.py              # both readings, both refusals, the clustering cost
python3 ec/tools/xdata_frame_credit.py --check      # the committed columns already encode the stated reading
python3 ec/tools/xdata_frame_credit.py --self-test  # named collapses, named refusals, the [writer]-tag trap
```

**The ruling: one committed `index.csv` row (one `out_file`) per function key.**
That is what the tool already did, and the block that says so is at the **end**
of `ec/tools/xdata_register_map.py` rather than in its docstring — not a
preference, but the constraint the two dated blocks already at the bottom of
that file record: the module is cited by line, `docs/findings.md` among the
citers, and the docstring sits above every one of those anchors. **No CSV is
regenerated by this change**, so `cluster_id` and `cluster_key` do not move, and
`readers`, `writers`, `single_function` and the Jaccard in `similar()` need no
code change: they already implement the stated reading.

Every input is a committed file — `index.csv`, the `.asm` listings,
`ec/decompiled/*/*.c`, `ghidra-functions.csv`, `xdata-symbols.csv`,
`xdata-registers.csv` and `ec/firmware/GMxMGxx_11.800`. No Ghidra run, no
scratch project, no hardware, no Windows, no network: no register was read and
no machine was observed. The tool writes nothing.

**There is no standing figure in this file.** Every number below is a transcript
of one run of the commands above, on this branch, quoted rather than kept. The
population moves as the export moves; `--self-test` and
`ec/tools/test_xdata_frame_credit.py` pin **claims and refusals**, never a count.

## 1. The two readings

A function key is `xdata_register_map`'s `(program, addr)` pair, and `scan()`
credits every occurrence in *that row's own* `.c` to it. So the three columns
are `len()` of sets of keys:

> **stated** — one committed row per `out_file`. The `0x036C` row names six
> keys, each named once, and no row is counted twice.
> **frame** — one frame of code. Where the export nests a listing inside
> another, both `.c` files decompile the same bytes, so the inner listing's
> credit goes to the frame holding it and the two are counted once.

The frame reading is not a contrivance. `ec/decompiled/index.csv` nests its own
frames ([`nested-export-frames.md`](nested-export-frames.md)), so the situation
it describes is the export's, not the tool's.

## 2. Why the frame reading is refused, and why that is not the whole reason

Collapsing a row onto "its container" needs a **single outermost container**, and
the census says there is not always one. Two shapes have none, and both are
refusals rather than a guess:

- **`several-containers`** — the row sits inside two or more containers at once.
  The census's own docstring records that in each such case the two containers
  fall in *different* buckets, so picking either would be wrong about the other.
- **`mutual-nesting`** — `common 0x6A02` (`FUN_CODE_6a02`, listed
  `0x6A02`-`0x6F5D`) and `common 0x6D46` (`FUN_CODE_6d46`, listed
  `0x67EC`-`0x6D69`). Each address falls inside the other's span and **neither
  span contains the other**, so the chain never reaches a row with no container.
  `frame_of()` follows a visited-set rather than a depth limit precisely so this
  is reported instead of being cut off at whatever row the search stopped on.

The tool prints, from one run:

```
  nested rows the census reports        69
  collapsible onto an outermost frame   56
  refused, and left on their own credit 13
    several-containers       7  common:0x6100, common:0x6116, common:0x6B94, common:0x6BAE, common:0x6BFF, common:0x6C70, ...
    mutual-nesting           6  common:0x6811, common:0x6817, common:0x6A02, common:0x6D46, common:0x6DB1, common:0x6E04
  of the collapsible rows, 32 are named by a register row; of the refused, 0
```

**Read that last line before treating the refusal as the argument.** It is
principled and it is not, on this tree, what decides anything: **no refused row
is named by any register row**, so nothing published would move even if every
refusal picked a container. The binding reason is the renumbering in §6.

The refusal still has to be *a* refusal rather than a coin-flip: a tool that
picked `0x6A02` for `0x6B94` would move real published credit on the strength of
a tie it could not break. That is `nested_frame_census.bucket_of()`'s "refusal
rather than a third bucket", reached from the other end.

## 3. Two of the collapses are not whole-listing ones

**"Its frame holds the row" is not the same as "its frame holds the row's
listing."** The census reads *address-inside-a-listing* — the container's span
reaches this row's address — and separately records whether it also swallows
this row's whole listing, which is its `span_contained` flag. The collapse
follows the first, because that is the relation the question is about, so a
collapse can be a **partial** one: the inner listing runs past the container's
last byte, the container's `.c` does **not** re-decompile the tail, and
collapsing the row would remove credit for statements no frame repeated.

The tool reports them rather than letting "collapsible" imply they are all the
same kind of thing:

```
  collapsible edges whose frame holds the row's address but not its whole
  listing -- the frame's .c does not re-decompile the tail, so collapsing
  them removes credit no frame repeated:
    common:0x1C3E -> common:0x1C14
    common:0x5E02 -> common:0x5DC2
```

`common 0x1C3E` is named by register rows, so this is not a shape that sits
outside the published columns. **It is not refused** — refusing would mean
refusing a collapse the census does support, on the strength of a predicate the
question did not ask about — but it is a second, independent reason the frame
reading is not simply applied: on that edge it is not a de-duplication at all,
it is a deletion.

## 4. The trap: the `functions` column is not a per-access record

The obvious way to answer the issue's question without re-running the census is
to count the `[writer]` tag in the CSV's own `functions` column. **That is
wrong**, and the reason is worth stating because the column looks like it
carries the answer:

- the tag is the function's **role** from `ghidra-functions.csv`, not a record
  of which of its accesses were stores;
- `entry["dirs"]` — the per-function bucket sets `scan()` already builds — is
  what reproduces the columns.

On `0x0491` the committed row reads `read 48`, `write 0`, `read+write 18`,
`writers 12`. Counting `[writer]` tags gives **2** against a derived 12. Across
the whole CSV the tags total **1606** where the `writers` column sums to
**5083**, and the two agree on only part of the rows. The tool derives from the
census and reads the CSV **only to be checked against**; `--check` asserts the
stated reading reproduces every committed cell.

**This corrects the issue's own wording on that row.** The issue says `0x0491`
is "a write to `0x0491` counted under both names". The nesting claim holds — one
edge, `bank1 0xBA43` inside `bank1 0xB98D`, and the row names both — but the
bucket name is wrong: the row's writers come entirely from `read+write`, and
**both** `0xB98D` and `0xBA43` read the address as well as writing it. Under the
frame reading the row goes 27 → 26 sources, 27 → 26 readers, **12 → 11**
writers.

## 5. What the frame reading would do to the columns

From the same run:

```
  rows the frame reading would change    82
    of those, 11 keep their count and only exchange one name for its frame
    largest drop: 0x0817 12 -> 5 functions
```

`functions_touched` moves on all 82, `writers` on 57 and `readers` on 47. **The
comparison is set-level, and that is the substantive choice**: a row can name a
nested frame *and* its container and keep the same count, so a size-only
comparison reports "no change" for a row whose `functions` cell loses one name
and gains another. Those are the 11.

**The issue's worked instance, `0x036C`.** Its two nested listings —
`bank1:0xE322 FUN_CODE_e322` and `bank1:0xE332 set_036c_to_4_jump_e490` — are
both held by `bank1:0xE2D3 dispatch_036c_low3_then_seed_1c00_block`. Under the
stated reading the row names all three; under the frame reading the two inner
names are gone, the holding frame stays, and the row goes 6 → 4 sources and
6 → 4 writers, with its readers unchanged. That is
`nested-export-frames.md` §6's "counted as frames that do not hold one another …
four such frames", measured.

**`0x0817` is the largest**, at 12 → 5: seven `bank0:0x900x` rows inside
`bank0:0x8FDB state_0817_fallthrough`, which is the container whose nine held
rows `nested-export-frames.md` §2 already uses for the `same-address` bucket.

## 6. Why the columns are not flipped: the renumbering

`similar()` takes the Jaccard of these same sets, so the frame reading
re-clusters the tree. Measured, and printed by the tool:

```
    program             components     cluster_key moves
    main-ec         389 -> 385                  298 addr(s)
    pd               50 -> 49                     3 addr(s)
```

**`cluster_key` is reported, not `cluster_id`,** because the id is a rank and
issue #253 is what a renumbering costs every page that names one — a figure in
the rank would understate what moves. `cluster_id` moves on considerably more
addresses than the key does, for the same reason the docstring gives at
`build()`.

So flipping the column is a tree-wide renumbering to land on a boundary the
export has not settled. That is the cost that keeps `--export-ownership` off,
measured in the same file on the same kind of relation, and it is the reason
`--collapse-co-readings` "writes nothing, because the group boundaries are a
hypothesis rather than a description". **The flip is not adopted here; it is
measured, and the measurement is what a future change would read before
deciding.**

## 7. The 872 bytes are a span overlap, not shared code

The issue's "whose committed listings share 872 bytes" is **exact as an address
range and wrong as a claim about the code**. `0x6A02`-`0x6F5D` and
`0x67EC`-`0x6D69` overlap over `0x6A02`-`0x6D69`, which is 872 bytes. Inside
that overlap the `6A02` listing decodes **243** bytes of instructions and the
`6D46` listing **36**, and the two cover the range very differently — `6A02`'s
last instruction inside the overlap is at `0x6AF3`, `6D46`'s at `0x6D68`.

So the overlap is the *reason* the two frames are hard to order, not evidence
that they are one routine — which is a point in favour of refusing the collapse
rather than performing it. Re-derive with:

```
python3 ec/tools/nested_frame_census.py --check      # the spans, the two readings, the mutual pair
```

## 8. What is not addressed here

- **Flipping the committed column.** §6 measures it and declines it.
- **Editing `ExportListing.java`, or any Ghidra script and any
  `--mode rebuild-project`.** The exporter's contract question is
  `nested-export-frames.md` §6's and it is left alone there.
- **The `0x1664` / #466 direction** — `functions_touched` *under*counting. A
  different mechanism; recorded not addressed, per that file's §8.
- **`xdata-export-ownership.csv`.** Its `shared` / `containment` vocabulary is
  whole-*file* containment and does not see this: the sharing here is
  statement-level. Both tools are named in §4 and neither was changed.
- **Any gate line in `.github/scripts/agent-gates.sh`, or any workflow or action
  edit.** Those files are template-copied and cannot be edited from a branch;
  `docs/agent-pipeline.md` carries the recipe. `bash tools/run-tests.sh` reaches
  the new suite by `find` with no workflow edit.
- **Anything requiring hardware, Windows, Ghidra or the network.** Nothing here
  needs any of them, and no live observation is claimed anywhere.
