# The two decompiling tools now read back the header their exporter wrote, and the class question has an answer

(2026-10-04. Static reading of committed files plus the four commands named
below. No image is opened beyond hashing the committed firmware, no Ghidra
project is touched, no register is read back, and no laptop, EC or Windows
machine is involved: every assertion in this change is over a committed file or
a `/tmp` fixture.)

## The claim

**Every generated `.c` in this repository carries a machine-written provenance
header naming the image it was exported from, and for the two `.c` trees the
shared exporter produces, each tool's own `--check` now reads that header back
and fails when it is missing, malformed, or names another image. Before this,
the answer to "is that decompile really out of the image we say it is?" rested
on a `find` over a naming convention.**

The negative it replaces is the one in
[`digest-docs-and-timings.md`](digest-docs-and-timings.md): "The measurement is
one command — `find . -name '*.annotated.c' -not -path './.git/*'` — and it
returns exactly one file, in `bios/`." That command searches a naming
convention, not a fact. It cannot distinguish "unedited tool output" from
"hand-edited and not renamed", which is exactly the shape CLAUDE.md's
calibration rule is about — a scan that finds nothing means *not found by this
method*, never *absent*. And the population at stake is the one the whole EC
reconstruction is made of: a `.c` under `ec/decompiled/` that was hand-edited
is blessed by `--write-digests`, and the message then tells the reader the file
"was truncated, overwritten or hand-edited" with nothing able to say which.

## Why the header and the digest answer different questions

`ec/ghidra/c-digests.csv` and `windows/ghidra/c-digests.csv` say a `.c` has not
moved. That is a fact about the *file*, and it is the right fact for the fault
it was built for: a truncated or half-overwritten export. `--write-digests`
computes it from whatever is on disk, which is why a hand edit has to be
re-blessed deliberately and shows up as a committed diff.

What no hash in those files carries is **which bytes the file was produced
from**. `--write-digests` will hash a `.c` left behind by an export of a
different firmware without complaint, because from its point of view the file
is a file. The decompile is then a reading of bytes this repository does not
claim to have read, and every other check over it — presence, digest, census,
the cross-decoder comparison — passes, because all of them are also facts about
the file.

The header is the only place that claim is written down:

```c
// bank1 @ F153   bare_ret_f153   [named]
// Ghidra 12.1.3 decompile, generated by ec/tools/build_ec_decompile.py -- do not edit.
// Source: ec/firmware/GMxMGxx_11.800, CODE bank 1 at file 0x10000 + the 0x0000-0x7FFF common area, SHA-256 158d1c6416426939a814146b766a44e2ff0e9286b0abd237e70e51a0c03399c4
// Machine output carrying this repository's symbols. Not the vendor's source.
```

That is `ExportDecompile.java`'s `writeFunctionFile()`, and the third line is
the load-bearing one. On the Windows side the same shape appears with the run's
whole target list paired positionally against that run's digests.

## What each check establishes, and what it does not

**What a green run says:** every committed `.c` under `ec/decompiled/` carries
the header `build_ec_decompile.py` writes, its `Source:` clause names the
program the file's own first line declares, its SHA-256 is the digest of the
committed firmware, and the `call-target` boundary caveat is present exactly
when the matching `index.csv` row's `seed_basis` says so. The same for every
committed `.c` under `windows/decompiled/native/`, where each named source
resolves to exactly one committed target in `native-binaries.csv` and each
digest a committed file records matches that record.

**What it does not say:** that any decompile is a faithful reading of the
firmware. A header that survives is not proof a file is unedited — a determined
edit rewrites the header too, and nothing here re-derives the C from the
firmware. What the check buys is what the digest buys and no more, a change has
to be made deliberately and shows up in the diff, plus the image the file names,
which the digest has no column for. It is a deliberate-change control and a
visible-diff control. It is **not** an anti-tamper control.

`verify_reassembly.py` remains the stronger claim on the EC listings and a
different question: it re-derives the listing bytes from the firmware, which is
a trusted input. The decompiled C has no such counterpart, which is why a
committed digest was needed there in the first place and why this check reads a
claim rather than re-deriving bytes.

**The limit on the Windows side, stated rather than hidden.**
`GamingCenter3_Cross.dll` — the retained export whose program is in
`decompile_native.py`'s `PROJECT_EXCLUDED`, because a 337 MB analysis database
is over GitHub's per-file limit — has no digest in either committed file:
`native-binaries.csv` records `runtime` for it and `manifest.csv`'s row carries
an empty `sha256` by construction. The only committed record of that binary's
digest outside the retained export's own header is `c-census.csv`, which is
derived from that header. So the check cannot confirm it, and says so on every
run rather than folding it into a pass — the same arrangement
`decompile_native.py --check` already uses for that file's missing `.asm`
listing. Its Ghidra version is unattributable for the same reason, since the
manifest row that would record it is the zeros a `not-in-project` row always
carries.

**The Ghidra version on the Windows side is asserted against what the export
recorded**, read from `manifest.csv` rather than held as a constant in the new
module: that driver derives its version from the installed Ghidra at run time,
so there is no constant to hold it against, and the committed record of what a
run used is the manifest. That is the whole of the claim.

## Which class of committed tool output is held, and why

The question worth answering once, because saying which class is held is what
stops the next one being an omission. Taken in turn:

**Held — the EC and Windows `.c` trees**, by the two checks this adds, over
every committed `.c` under `ec/decompiled/` and
`windows/decompiled/native/`. Both are produced by the shared
`ExportDecompile.java`, both carry the provenance header, and both are read
against the clauses their own `write_context()` composes.

What the checks hold against the exporter's *wording* is held too, which is
the second half of the same discipline and the reason neither module can drift
from the Java. Each reads the string literals out of `writeFunctionFile()` and
`writeHeader()` and requires every literal it spells out to be one of them; the
EC module additionally reads the boundary caveat out of `writeBoundaryCaveat()`
rather than restating it. That is the arrangement
`build_ec_decompile.py`'s `placeholder_name_tests()` already uses to hold
`TongFang.java`'s `isPlaceholderName()` against the Python that reimplements it,
for the same reason: a Python copy of a Java literal is a second definition of
it, free to drift. Without it, a rewording in the Java would leave the check
red on a tree the exporter wrote correctly — the failure mode of a check that
is one merge behind its subject.

**Not held, and the class this mechanism would fit next — the BIOS listings**
under `bios/ghidra/listings/`. `DecompAll.java` is not their exporter: it writes
`bios/decompiled/*.c`. The listings are `.asm` files from
`ghidra/scripts/ExportListing.java`, dispatched by `bios_extract.py`, and each
one opens with the same header block the EC listings carry — name and address,
the `generated by` line, the `Source:` clause and its digest, then the
machine-code caveat:

```asm
; DxeOverClock @ 00000260   FUN_00000260
; Ghidra 12.1.3 disassembly, generated by bios/tools/bios_extract.py -- do not edit.
; Source: GM7MG7P/GMxMGxxN109A08.ROM, DxeOverClock.efi (PE32 body, RVA space), SHA-256 dfe8047f35bb1125bbb45d69c96ad83d64e59dd5e50b8d88052c0db04a2d920e
; This is the machine code. The decompiled C for this address is 00000260.c in the same tree;
; where the two disagree, this file is right and the C is a reading of it.
```

The digest names `GM7MGxxN109A08.ROM`, and those bytes are committed: they are
member `GM7MG7P/GMxMGxxN109A08.ROM` of the git-tracked
`vendor/bios-1.09/BIOS_1.09.zip`, and `bios_extract.py`'s `rom_digest()` reads
them straight out of that zip. Its `--check` already holds the manifest's
`sha256` column against that digest, so the header's digest has an independent
committed oracle and nothing about the class resists this mechanism.

What is true today is narrower, and worth stating precisely rather than as
"unholdable". No checker reads those headers back; `verify_reassembly.py`'s
`LISTING_PATHSPEC` is `ec/decompiled/**/*.asm`, so the byte re-derivation that
covers the EC listings does not reach this path; and `c-digests.csv` is scoped
to `bios/decompiled`, so it holds the BIOS `.c` files and not the listings
beside them. Each of those is a place a follow-up could start, and none of them
is in this change.

**Not held, and not holdable this way — the `.cs` under
`windows/decompiled/`**. These come from `ilspycmd`, whose output carries no
provenance header at all: the first line of a committed `.cs` is a `using`
directive. There is nothing to read back. Holding them would mean either
generating a header this repository does not generate, or digesting them — a
different mechanism from the one this change adds, and the reason the `.cs` are
not covered by naming them here.

**Held, and deliberately hand-written — `bios/decompiled/*.annotated.c`**, the
readable restatement whose convention is `bios/README.md`. It is not tool
output, so there is no header to read; it is digested like everything else and
`bios_extract.py`'s `HAND_EDITED_C` is what makes its digest failure read as
"behind" rather than "damaged".

**A case this change does not touch: the BIOS `.c` files.** They carry a
different header again — `DecompAll.java`'s
`// <module>.efi: Ghidra <language-id> decompile, unedited` — with no
`Source:` clause and no digest, and they are held by `bios_extract.py`'s
`c-digests.csv` the way the other two trees are. There is no image claim in
them to read back, so holding their provenance would need a header
`DecompAll.java` does not write. That is a follow-up, not this change.

**None of the unheld classes is in this change**, and nothing above should be
read as saying they are covered.

## Re-deriving it

Four commands, all of which read committed text and none of which needs a
network, a Ghidra project or a hardware run:

```console
$ python3 ec/tools/build_ec_decompile.py --work "$(mktemp -d)" --check
$ python3 ec/tools/build_ec_decompile.py --work "$(mktemp -d)" --self-test
$ python3 windows/tools/decompile_native.py --check
$ python3 windows/tools/decompile_native.py --self-test
```

Both `--check` runs print a `header:` line naming what they compared; both
`--self-test` runs execute the fixture cases, each mutating one header in a
`/tmp` fixture and asserting the refusal names the file, because a check that
has quietly started accepting everything looks exactly like a check that is
working. `bash .github/scripts/agent-gates.sh` runs both modes of both tools,
so this is CI surface without a gate edit: `check_ghidra_tooling()` already
dispatches them.

**No count of these files is stated here**, and the new tools print what they
measured rather than the write-up holding the figure: the counts move on every
export, and a line carrying one is a line every later merge has to touch.
`find ec/decompiled -name '*.c' | wc -l` and its Windows equivalent are the
commands.

**A guard that only ever sees bad input cannot tell "clean" from "never ran."**
Each module's `self_test()` therefore runs a fixture carrying a correct header
first and asserts it produces no problems, before any mutation.
