# `diff_table()` names every row of a permuted table, including the rows that did not move (issue #469)

Issue [#462](https://github.com/ElDavoo/tongfang-gm7mg7p-re/pull/462) added
three rejection assertions to `call_graph.py --self-test()` and presented them
as the evidence that `--check` still rejects. None of the three can detect a
diff that pairs rows by position, because an in-place cell edit, a dropped
last row and a **moved** row all leave the surviving pairs aligned under a
positional zip. This file adds the case that separates them, and records what
it measures on the tree it was written on (2026-10-03).

**The defect is reproduced, and it is `diff_table()`'s to fix — issue #459's.**
The zip in `diff_table()` is untouched by this change. What is added is the
assertion that goes red when #459's keyed fix lands, and which reads `ok` when
it does, with no edit to it.

**Nothing here is a behavioural claim.** No register, no `status:` change, no
annotation row, no EC image, no hardware and no Windows. This is a
self-test assertion plus a text measurement over `call_graph.py`'s own fixture
and its own committed CSV, and the CSV is byte-identical — `--check` is
§Reproducing's own pass condition.

## Reproducing

Everything below comes from driving the shipped functions in a throwaway
interpreter, never from a re-implementation. From the repository root:

```python
import os, sys
sys.path.insert(0, "ec/tools")
import call_graph as cg

index = cg.load_index(os.path.join(cg.FIXTURE, "index.csv"))
edges, _unresolved, _orphans, _total, listings = cg.scan(
    index, os.path.join(cg.FIXTURE, "decompiled"))
cited, _rejected, _undecided, _kept = cg.citations(
    index, listings, os.path.join(cg.FIXTURE, "ghidra-functions.csv"))
rows = cg.build(index, edges, cited)
rendered = cg.render(rows)

permuted = rows[1:] + [rows[0]]                    # row 0 moved to the end
lines = cg.diff_table(cg.render(permuted), rendered)
named = {(m.group(1), m.group(2)) for m in
         (cg.ROWHEAD.match(l) for l in lines) if m}
print(len(named), sorted(named),
      cg.check_table(cg.render(permuted), rendered)[0])
```

On the fixture, 2026-10-03: `13` rows named, the moved row `common/07D0`
among them, `check_table` returns `1`. **All thirteen rows of the table are
named and exactly one of them moved.**

## What the committed table does, and the cap that hides the worst of it

The same rotation on the committed `call-graph-callees.csv`, re-rendered
through `render()` so the comparison is between two tables this tool wrote:

| driving | table | result |
|---|---|---|
| rotate row 0 → end, fixture | 13 rows | **13 rows named** — every row, including the 12 that did not move |
| rotate row 0 → end, committed CSV | 1,841 rows | **20 rows named**, then `... more` |

**On the committed table the moved row is never named.** `diff_table()` stops
at its `shown >= 20` display cap, and the moved row — `bank0/DFA0` today — sorts
past the twentieth. So the failure is worse on the real table than on the
fixture, not milder: the fixture's 13 rows are all under the cap, so the
fixture reproduces the defect's *shape* and not the symptom the real table
shows. The first row named on the real table is `bank1/D16F`, a row that did
not change.

### The issue's 154 is not reproducible, and the reading it names is capped

The issue reports the call returning "**154** differing rows" on the committed
table. It does not reproduce here, and the number cannot come from the reading
the issue describes. The named count is capped at 20 by construction, so 154 is
not reachable from it; counting differing pairs with the cap lifted gives
1,841, which is every row; and counting printed lines gives fewer than either.
**The qualitative claim reproduces and the numeral does not**, and the two are
the same defect at different move scales — this is **not** a correction of
#459's own "743 of 1,841", and nothing here should be read as one.

**Every figure in this file's two tables is a measurement of the committed
inputs on 2026-10-03, not a property of the tool, and none of them is held
here as a standing fact.** The committed CSV is regenerated by every tranche
PR and the fixture is a hand-written tree, so a reader whose tree carries a
later one re-derives by the command above rather than carrying these forward —
which is the rule `call-graph.md`'s own counts section already sets for itself.
The *shape* is what does not move: for any *N* > 2 a one-row rotation makes a
positional zip name *N* rows, so a fixture or a table of any size above two
shows this, and the two numbers that matter — rows named, and whether the moved
row is among them — are what `--self-test` prints on every run.

## Why the three existing assertions cannot see this

Each is aligned by construction, which is the whole of why a positional zip
passes all three:

- **One cell altered, in place.** `edited[0]["inbound"]` changes the value of
  row 0 and leaves row 0 at index 0, so a positional zip compares it against
  row 0 and the assertion sees what it expects. The same is true under a keyed
  `(scope, addr)` zip, so the assertion does not distinguish the two strategies
  either — it is a real assertion about a cell edit being *reported*, and it is
  not an assertion about alignment.
- **Last row dropped.** Every one of the first *n-1* pairs stays equal under
  either strategy, so the diff sees only the row-count line and the assertion
  passes unchanged. Correct, and equally blind to pairing.
- **CRLF, and the table against itself.** The first is a byte-level case the
  row diff is *supposed* to find nothing in, and the second is `--check`'s
  passing case. Neither moves a row.

The **rendered table against itself** assertion is `--check`'s passing case and
is the reason the fixture's own bytes are worth pinning. It is not a rejection
case at all.

## The assertion

Added to `self_test()` in `ec/tools/call_graph.py`, immediately after the
last-row-dropped case so the rejection cases read together. It is driven
through the shipped `diff_table()` and `check_table()` rather than a
re-implementation, for the reason `diff_table()`'s own docstring gives: an
assertion against a re-implementation would prove the re-implementation works.

Three clauses, in one condition:

1. `check_table(permuted, rendered)` still returns `1` — the permutation is
   still rejected, which is true today and true after the fix.
2. the set of rows `diff_table()` named is a **subset of the moved row**.
3. that set has **at most one** member.

Clauses 2 and 3 are the ones that fail today. The neighbouring assertion pins
that the same parse reads a header it is meant to read, so clause 2 cannot pass
by parsing nothing.

### Why "at most one" and not "exactly the moved row"

A keyed `(scope, addr)` zip compares every row of a pure reorder **equal**, so
`diff_table()` returns **zero** rows; asserting the moved row is named would
fail against that fix and force #459 to edit the assertion — the coupling the
issue asks to be avoided. "At most one, and only the moved row" is satisfied by
that fix and is still fatal to the positional zip, which names every row.

**A limit on that, stated because it was measured.** A keyed fix that *also*
reports a row whose **index** changed does not satisfy clause 3 either: a
one-row rotation changes the index of *every* row, not just the one that was
picked up and moved, so such a fix names the whole table and this assertion
goes red against it. That is a real constraint this places on #459 rather than
a hypothetical one, and it is recorded here rather than left for #459 to
discover. If #459 wants to report position changes, this clause is the thing
to revisit, and the choice belongs there.

### What the fixture cannot cover, and why the real table is not used instead

The assertion runs on the fixture. `--self-test`'s contract is the fixture —
its docstring and `ec/tools/testdata/call-graph/README.md` both say so — and
reading the committed CSV inside it would couple the assertion to a file every
tranche PR regenerates, which is the opposite of what a fixture is for. The
property is also scale-free: for any *N* > 2 a one-row rotation makes a
positional zip name *N* rows, so a fixture of a few rows already demonstrates
it and a table of thousands adds nothing to the demonstration.

What the fixture cannot reach is `diff_table()`'s 20-row **display cap**, and
that is where the worst symptom lives — the moved row never named. Two
consequences, both for #459 and neither fixed here:

- the cap's interaction with a keyed diff is unpinned;
- if a keyed fix returns no rows for a pure reorder, `check_table()`'s
  byte-level fallback fires and reads *"line endings, a trailing blank line,
  **column order** or quoting differ"* — a whole-row reorder is none of those,
  so that message would be wrong for the one drift it becomes the sole reporter
  of. **#459 should decide whether a reorder belongs in that message.**

Widening the fixture past the cap is deliberately not done: it would add rows
whose only job is to cross a display threshold, and every assertion depending
on their positions would re-break whenever the fixture changed.

## The exit code is 0, and that is the judgement call

`call_graph.py` is in the cheap gate's tool list, and its arm is
`python3 "$tool" --check && python3 "$tool" --self-test || rc=1`. A plain
assertion that fails today turns **every** commit's cheap tier red until #459
lands, and nothing in the pipeline merges meanwhile — a worse outcome than a
visibly outstanding defect, and this repository has taken that trade before,
in [`0751-grader-self-test-gate.md`](0751-grader-self-test-gate.md).

So the assertion prints through a second printer beside `check()`:

- the verdict is prefixed **`FAIL known defect (#459)`**, never `ok`;
- the measured symptom goes on the next line — `named 13 rows, expected at
  most 1, and the moved row common/07D0 is among them` — so a run says what is
  wrong, not only that something is;
- `ok` is **not** cleared, so `self_test()` still exits `0` and the gate arm
  stays green;
- when #459's keyed zip lands, `cond` becomes true, the line reads `ok`, and
  **the assertion needs no edit**. That is the issue's own "done looks like",
  and it is why the clause is phrased as a property rather than as a
  re-implementation of one particular fix.

**The tail changes with it.** `self_test()` ended `all assertions passed`
whenever `ok` held, which with a known defect outstanding is verbatim the
complaint in this issue's title. It now prints `all assertions passed; 1 known
defect outstanding (issue #459)` while one is, and the plain
`all assertions passed` only when none is.

This is the one place the literal reading of the issue — *the new assertion
fails on the current code* — is deliberately not taken on the **exit code**.
The assertion does fail on the current code and says so on every run. A human
who wants the plain red assertion instead is looking at one line in
`check_known_defect()`: drop the `ok = False` it does not set, and the gate's
arm goes red for the whole queue until #459 lands.

needed because the tool already runs in both modes.
