# `0x1663`, `0x1667` and `0x1668`: the rest of the `0x1663`-`0x1668` run, and a third accessor the census cannot see (issue #635)

Issue #267 named `0x1665`, `0x1666` and `0x166A` — three single-bit test bytes
in the bank0 run at `0xC251`-`0xC4E7` — and gave each a `registers.yaml` row
with a per-site polarity map. The same run holds three more that it did not
name, and their own annotation rows said so in as many words: `0x1663`,
`0x1667` and `0x1668`. These are their rows.

The interesting result is not that they were unnamed. It is that **one of the
three has a third accessor that no committed table had counted**, on a different
bit from the two the annotation rows describe, and that it sits in a routine no
export in this repository covers.

## The bit map

Every site is the same seven-instruction shape — `mov DPTR,#addr` /
`movx A,@DPTR` / one bit test / `mov R7,#1` / `ret` / `mov R7,#0` / `ret` —
with no `inc DPTR` walk, no store and no call. The polarity is the *name*, so
it is given per site rather than as a blanket "inverted".

| addr | site | instruction | R7 = 1 when | polarity |
|---|---|---|---|---|
| `0x1663` | `0xC184` | `jb 0xe3, 0xC18E` | bit 3 **clear** | inverted |
| `0x1663` | `0xC1B1` | `jnb 0xe6, 0xC1BB` | bit 6 **set** | not inverted |
| `0x1663` | `0xC1BE` | `jb 0xe6, 0xC1C8` | bit 6 **clear** | inverted |
| `0x1667` | `0xC349` | `jnb 0xe0, 0xC353` | bit 0 **set** | not inverted |
| `0x1667` | `0xC356` | `jb 0xe0, 0xC360` | bit 0 **clear** | inverted |
| `0x1668` | `0xC412` | `jnb 0xe4, 0xC41C` | bit 4 **set** | not inverted |

Five of the six rows are read off committed `.asm` listings. The sixth,
`0xC184`, is read off the image, and §"The third accessor" is why that is a
different claim rather than a stronger one.

**The two `0x1663` entries on bit 6, and the two `0x1667` entries, are exact
complements** — the mirror-accessor pair #267 recorded for `0x1665`, where a
routine tests one bit both ways round. Their agreement is a result, not a risk
to guard against: it is what the same test written twice is supposed to look
like. `0x1668` has one site and therefore no second polarity to compare
against, which is a limit on what a single reading can tell us rather than a
finding.

## How the run is reached, which the issue asked about

Every one of the five committed sites has a caller, and **the two mirror pairs
are called from opposite arms of one state machine** — which is what makes them
a mirror accessor rather than a duplicate:

| site | called from | reached when |
|---|---|---|
| `0xC1B1` `test_1663_bit6` | bank0 `0x8F20` | bit 0 of `0x0815` is set |
| `0xC1BE` `test_1663_bit6_inverted` | bank0 `0x8FDB` | `0x0817` is 2, via `dec A` / `jz 0x9031` |
| `0xC349` `test_1667_bit0` | bank0 `0x8F20` | `0x0817` is 2, via `dec A` / `jz 0x8FA3` |
| `0xC356` `test_1667_bit0_inverted` | bank0 `0x8FDB` | bit 0 of `0x0815` is clear |
| `0xC412` `test_1668_bit4` | bank0 `0xAB6E` | `read_06e6_xor_01` returned 0 |

`0x8F20` calls the non-inverted member of both pairs and `0x8FDB` calls the
inverted member of both, which is what makes them a mirror accessor rather
than a duplicate: one caller wants the bit and the other wants its complement.

**The selecting byte is not one blanket statement, and getting that wrong
would have been a real error.** `ec/decompiled/bank0/8F20.asm` opens the
choice between the two arms at `8F34` — `mov DPTR,#0x815` / `movx A,@DPTR` /
`jb 0xe0, 0x8f3e` — so the arm is selected on **bit 0 of `0x0815`**, and
`0x0817` is not read until `0x8F44`, *after* the `lcall 0xc1b1` has returned.
`0xC1B1` is the target of the `lcall` the `jb` branches to at `8F3E`, and
`0xC356` is the target of the `lcall` that is `0x8FDB`'s first instruction,
reached unconditionally by the `ljmp 0x8fdb` at `8F3B` when bit 0 falls clear,
so it is selected on `0x0815` rather than dispatched on `0x0817` at all. Only
the two later sites — `0xC349` at `0x8FA3` and `0xC1BE` at `0x9031` — are
genuinely `0x0817`-dispatched, each through its own `dec A` / `jz` chain
(`8F55`-`8F5D`, `8FF5`-`8FFD`).

`0x0817` has no entry in `ec/annotations/registers.yaml`, so **what the state
encodes is not decoded here** — the arms are identified, their meaning is not.

`0x1668`'s single site is the only one of the six with a consequence visible in
a committed listing: `0xAB6E` calls it and then clears bit 0 of XDATA `0x06E2`
when its argument is non-zero, or sets it and calls
`set_0751_and_07a6_bits` when the argument is zero and bit 0 was clear. What
bit 4 of `0x1668` *means* is still not decoded; only that this one site is not
a leaf.

**`0xC184` is the exception.** It has no committed listing and therefore no
committed caller, so it is the one site of the six whose reader is not
established here.

## The third accessor, at `0xC184`

`ec/tools/trace_xdata_refs.py ec/firmware/GMxMGxx_11.800 0x1663 --csv` finds
**three** `MOV DPTR,#0x1663` sites where the committed
`ec/annotations/xdata-registers.csv` reached two:

```
0x1663,0x0C184,bank0,0xC184,24,0,read x1,"movx a,@dptr ; jb acc.3,+0x03"
0x1663,0x0C1B1,bank0,0xC1B1,24,0,read x1,"movx a,@dptr ; jnb acc.6,+0x03"
0x1663,0x0C1BE,bank0,0xC1BE,24,0,read x1,"movx a,@dptr ; jb acc.6,+0x03"
```

Its thirteen bytes read off the image are a complete accessor ending exactly
where the next annotated function begins:

```
C184     90 16 63 mov      DPTR, #0x1663
C187     e0 - -   movx     A, @DPTR
C188     20 e3 03 jb       0xe3, 0xC18E
C18B     7f 01 -  mov      R7, #0x1
C18D     22 - -   ret
C18E     7f 00 -  mov      R7, #0x0
C190     22 - -   ret
C191     90 16 03 mov      DPTR, #0x1603      <- set_1603_bit4
```

Three things follow, and only the first is about this repository.

**It is reached from another bank, but that is not what distinguishes it.** The
forwarder onto it is the bank1 trampoline at `0x1AB6` (`mov DPTR,#0xC184` then
`ljmp 0x1100`), and `ec/annotations/forwarder-targets.csv` classes the address
`no-listing` — *not found by this method*: no committed export names it in
bank0, which is an unseeded function rather than a verdict about the bytes.
All three of this byte's sites have a bank1 forwarder onto them, the same
six-byte mechanism — `0x1A26` onto `0xC1B1` and `0x1A2C` onto `0xC349` are
rows in the same census, classified `entry` because those two targets do have
exported listings. So cross-bank reachability is the run's ordinary shape, and
what makes `0xC184` different is that it is the one whose target no committed
export covers. That classification and its first eight bytes were already
committed; what is new here is that the bytes are a `0x1663` accessor.

**It tests a different bit from the pair beside it.** Bit 3, not bit 6, and
inverted. So `0x1663` is not three copies of one flag read three ways. Whether
bit 3 and bit 6 are two halves of one thing, or unrelated, is **not determined
here** — nothing committed reads either bit a second time.

**Two tools now resolve it, and it is worth being exact about which found it
first.** `ec/annotations/forwarder-targets.csv` already carried the address and
its opening bytes — `90 16 63 e0 20 e3 03 7f`, which spell `mov DPTR,#0x1663`
and a bit-3 test — classified `no-listing` because the question that census asks
is which bank a forwarder's target resolves in, not what the target reads. What
no committed table did was count it as a `0x1663` reference site.
`trace_xdata_refs.py` does that now, from the image and without needing a
`registers.yaml` row; `check_site_resolution.py` resolves it too, but only
*because* this change gave the byte a row, so it is a consequence here rather
than an independent discovery. Of the six rows the three new addresses
contribute to `site-resolution.csv`, this is the one labelled `not exported`.

## The two methods, compared in composition as well as in total

Issue #267 asked for this comparison because its own `XDATA_1665` row found the
two methods agreeing on a total while disagreeing about composition — the
C-level method double-counting `0xC278` and missing `0xC4E7`, landing on the
right number by two errors. So a matching count is not the test.

| addr | image sites (`trace_xdata_refs.py`) | C-level refs (`xdata-registers.csv`) | agree? |
|---|---|---|---|
| `0x1663` | 3 — `0xC184`, `0xC1B1`, `0xC1BE` | 2 — `0xC1B1`, `0xC1BE` | **no** |
| `0x1667` | 2 — `0xC349`, `0xC356` | 2 — `0xC349`, `0xC356` | yes, in composition |
| `0x1668` | 1 — `0xC412` | 1 — `0xC412` | yes |

**`0x1667` and `0x1668` do not carry the artifact, and that is worth recording
as the positive result.** For those two the two methods agree in count *and* in
composition, and did before this change as well as after: every site the image
holds is a site an exported function covers. Nothing about them needed fixing.

**`0x1663` does carry it, in the shape `0x1665` did not.** The C-level method
misses `0xC184` entirely, because the routine has no exported `.c` at all — the
blind spot #267 hit at `0xC2C2` and `0xC4E7`. The difference is what happens
when you close it. `0x1665`'s gap was a double-count in one place cancelling a
miss in another, so seeding its sites fixed the total and left the composition
wrong. `0x1663`'s gap is a **pure miss**: there is no surplus to cancel it, and
seeding `0xC184` would make the two methods agree in count and in composition
at once.

This change does not seed it. The two numbers therefore stand side by side and
are both right about their own method:

- `ec/annotations/registers.yaml` records `static_refs: 3` for `0x1663`,
  because `check_register_counts.py` recomputes that figure from
  `ec/firmware/GMxMGxx_11.800` and the image holds three sites.
- `ec/annotations/xdata-registers.csv` keeps `refs 2` for `0x1663`, because
  that is this census's own count over exported functions.

Seeding `0xC184` — an annotation row, a re-export, and the `.c` it produces —
is the follow-up, and it is the one piece of this issue's work that was left.

## The DSDT

A fact about the ASL text, not a scan result. The `ECMG` field list is
`evidence/acpi/dsdt.dsl:52194-52328`; its 28 `Offset` declarations run from
`0x043E` to `0x0EA0`, and all three bytes here are above the highest of them.
They are EC-internal and invisible to ACPI. `XDATA_1665`'s note is the model
for the phrasing, and it also carries the correction worth repeating here: an
earlier version of that sentence claimed a whole-file grep for the address
returned nothing, which six committed listings refuted.

## What was not done

No hardware and no Windows machine is reachable from this pipeline, so nothing
below was observed:

- **No status promotion.** All three stay `present-untested`. A static walk
  supplies references, not behaviour.
- **No writer found, and none claimed absent.** Both committed methods find no
  write to any of the three. That is *not found by this method* on `XDATA_1665`'s
  terms — a computed `DPH` or an indirect `movx @Ri` is invisible to both
  scans (#110) — and a byte only ever read must be written by something.
- **What the bits mean is still open.** Bit 6 of `0x1663` has a mirror pair and
  bit 3 does not; whether that is a relationship is not determined here. That
  needs a human at the machine.

## Reproducing

```sh
python3 ec/tools/trace_xdata_refs.py ec/firmware/GMxMGxx_11.800 0x1663 0x1667 0x1668 --csv
python3 ec/tools/check_register_counts.py ec/firmware/GMxMGxx_11.800
python3 ec/tools/check_site_resolution.py ec/firmware/GMxMGxx_11.800 --csv
grep -n '0x166[367]' ec/annotations/xdata-registers.csv
```

## Follow-ups this raises

- **Seed `0xC184`** as `test_1663_bit3_inverted`, which closes the
  two-methods gap in count *and* composition for the first time in this run.
  It needs an annotation row and a re-export, nothing more.
- **What reads `0x1663` bit 3**, and whether it is the same thing bit 6 is.
  `0xC184` has no committed caller; the bank1 trampoline at `0x1AB6` is the
  only committed reference to it.
- **What the `0x0817` state machine is.** Both mirror pairs are reached from
  the same two arms and both later members are dispatched on this byte, so
  decoding it would decode the run around them. `0x0817` has no
  `registers.yaml` entry and is written by `0x902A` (`write_2_to_0817`),
  among others. The arm itself is chosen on bit 0 of `0x0815`, which is the
  other half of the same question.
- **The unexported bank0 window around it.** `0xC184` is one address; whether
  the trampoline family at `0x1A98`-`0x1ABC` reaches more unseeded routines is
  the wider question, and `docs/findings/forwarder-target-bank-census.md`
  already carries the census that would answer it.
