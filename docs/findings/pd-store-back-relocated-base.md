# What the PD image's running `0x0D`/`0x0E` base relocates: a cursor walked by small displacements, read from all 81 store-back callers (issue #1237)

**Read the headline before anything else.** Everything below is about the
`ITE8850-PD` image at file `0x20000` — a second, self-contained 8051 program
with its own XDATA map and its own internal-RAM direct space. It says
**nothing** about the EC's `0x0D`/`0x0E`, which are a different program's
variables in a different program, and `ec/annotations/registers.yaml` is
untouched by this work and deliberately so. All of it is static analysis of the
committed `ec/firmware/GMxMGxx_11.800`. No register was read back, no write was
attempted, nothing ran on the machine.

`../../docs/findings/pd-direct-offset-pointer-add.md` settles that direct
`0x0D`/`0x0E` hold a **running** 16-bit base in that image's internal RAM —
`0x27FF` loaded at reset, advanced by every execution of the `0x122F` store-back
entry, read by the `0x1253` add at its callers — and names in its §8 item 1 what
it does not establish: *"What the running base relocates. … Naming the structure
it indexes needs either a live trace or a caller-by-caller reading of the 81
sites."* **This is that reading**, and it is the half that turns a mechanism
into a fact about the image.

**What it concludes, and at what strength.** The base is a **displacement base
into a record-like structure the firmware walks by small negative offsets**, not
a relocated table base — an inference from a displacement distribution measured
over the committed image, labelled as an inference, with the record's contents,
width and count left open (§6). **Much of the reading is not new to the
repository**: committed annotation names already spell several of these loads
(`set_dptr_ffff_tail_jmp_122f`, `call_122f_with_dptr_fffd_6f96`,
`load_dptr_fffe_into_0d0c`), and §4 says how far that goes and where it stops.
What is new here is the *census* and the *baseline*: no committed row recorded
that all 81 callers cluster, or what that clustering is against.

## 1. Reproducing this

Every figure below comes from one of these, from the repository root:

```console
$ python3 ec/tools/pd_store_back_dptr.py ec/firmware/GMxMGxx_11.800

                     the region's 3176 `mov dptr,#imm16` immediates -- the baseline, and

$ python3 ec/tools/pd_store_back_dptr.py ec/firmware/GMxMGxx_11.800 --check

```

(The `...` stands for the values histogram, the committed-listing comparison
and the closing paragraphs, none of which the argument below needs quoted
whole.)

`--sites` prints one line per candidate and `--csv` writes
`ec/annotations/pd-store-back-dptr-sites.csv`, the row-per-candidate table
every figure here is measured from. The tool **imports** `fold_back()`,
`dptr_before()`, `entry_pick()` and `entries()` from
`ec/tools/pd_direct_offset_sites.py` rather than re-deriving them, so
`DPTR_SCAN` and `FRAME_BACK` are the same constants the parent's figures were
measured with, and the entry is *derived* rather than written down as `0x122F`.

## 2. The adjacency, which is what makes this more than "in range"

The issue asked for the DPTR each caller loaded, and `dptr_before()` returns it
with a **gap**: how far back the `90 hi lo` byte pattern sits. The gap is the
whole strength of the reading, so it is stated first and pinned.

**Every one of the 81 candidates has its load at gap 3**, so the byte at
`site-3` is `0x90` for every one. That is adjacency, not proximity.
`mov dptr,#imm16` is exactly three bytes long, so a load at gap 3 *is* the
instruction immediately before the transfer. A gap of 0 in the parent's
vocabulary — a load anywhere in the 32-byte window — would be equally consistent
with a load 32 bytes back in unrelated code; a gap of 3 is not.

Two of the corroborated sites show it in committed text, whole:

```console
$ cat ec/decompiled/pd/717C.asm
; pd @ 717C   set_dptr_ffff_tail_jmp_122f   [named]
; Ghidra 12.1.3 disassembly, generated by ec/tools/build_ec_decompile.py -- do not edit.
; Source: ec/firmware/GMxMGxx_11.800, the ITE8850-PD image at file 0x20000 -- a separate program with its own address space, not a third bank, SHA-256 158d1c6416426939a814146b766a44e2ff0e9286b0abd237e70e51a0c03399c4
; This is the machine code. The decompiled C for this address is 717C.c in the same tree;
; where the two disagree, this file is right and the C is a reading of it.

717C     90 ff ff mov      DPTR, #0xffff
717F     02 12 2f ljmp     0x122f
```

`0x717F` loads `0xFFFF` and transfers, three bytes apart, in a listing a reader
can check by eye without running anything.

## 3. The distribution, and the baseline it is read against

Read as a two's-complement displacement from the running base, the immediates
run `-34 .. +35`. The two bands are **50 negative** and **31 positive**, and the
concentration is at the near end: `-1` ×17, `-4` ×13, `-3` ×9, `-2` ×5, then a
thin positive tail and one `+0x23`.

**The baseline is the number that makes this a finding.** The same band test
applied to *every* `mov dptr,#imm16` in the region — 3,176 of them — puts
**7.8%** inside `-0x23 .. +0x23`. At the 81 store-back sites, **100%** do. A
band is not remarkable on its own; a band that thirteen of every fourteen
`mov dptr` immediates in this image fall *outside* of is. Without that
comparison "the immediates cluster" is a shape a reader could equally get from
a scan that had found the wrong bytes.

The `0x1253` add sites, read the same way, resolve at **32 of 33** — one has no
`mov dptr` in the window, which is "not found by this method", not a site that
loads nothing. **Every resolved one is positive**, running `+3 .. +0x28`. That
contrast is the point of §5: the store-back entry walks *back*, the read-only
add walks *forward*.

## 4. Three checks that the reading is not an artefact

### 4.1 The committed listings

Twenty of the 81 sites are transfers a committed `ec/decompiled/pd/*.asm`
actually decodes, and **all twenty are among the byte scan's candidates** — the
parent's §2 reconciliation re-confirmed from the other direction, by site
rather than by count. The byte scan's known failure is phantoms: three bytes
inside some other instruction. **A decoded listing cannot be a phantom in that
particular way**, because the exporter cut it on an instruction boundary. So the
concentration is not the scan mistaking one instruction's tail for another.

`--sites` grades this rather than rounding it up, because the two halves can
disagree; the `in_committed_listing` column of the committed table carries the
same grade per row:

| grade | rows | meaning |
| --- | --- | --- |
| `both` | 19 | one decoded listing holds the load **and** the transfer — adjacency confirmed by text |
| `transfer only` | 1 | a listing decoded the transfer; the load falls outside every listing |
| `no` | 61 | the byte scan alone |

The single `transfer only` row is `0x7059`, and **it is the case that keeps the
other grade honest.** Its committed annotation (`ghidra-functions.csv`,
`pd,7059,call_122f`) reads: *"A single lcall 0x122F with no setup of its own:
DPTR and R0-R7 are whatever the caller left."* The byte scan says the
immediately preceding instruction is `90 ff ff`, a `mov dptr,#0xFFFF`.

Both statements are about a different thing, and neither is refuted by the
other. The annotation describes *the function Ghidra recovered*, whose listing
begins at `0x7059`; the scan describes *the byte stream*, in which `0x7056` is
three bytes earlier. No committed listing covers `0x704B`-`0x7058` — the
recovered functions step from `0x7045` straight to `0x7059` — so whether
`0x7056` is code that runs before that transfer or a data byte that happens to
look like one is **not settled by anything in the repository**, and this file
does not settle it. What it does do is refuse to grade the row a `both`.

**This is the honest boundary of §2.** Gap 3 says the load is the immediately
preceding *instruction*. Whether control reaches it by falling through from the
previous routine or by arriving at `0x7059` as a call target is control flow,
which this repository has deliberately not attempted to recover
(`ec/README.md`, "toolchain proven, not attempted"). For 19 rows a decoded
listing settles the question; for the other 62 it does not.

### 4.2 The committed annotation names

Several of the 81 sites already carry a committed annotation row whose name or
comment spells the loaded immediate, and **every one matches what the scan
finds**:

| annotation row (`ec/annotations/ghidra-functions.csv`) | sites | loads |
| --- | --- | --- |
| `set_dptr_ffff_tail_jmp_122f`, `dptr_add_0d0e_via_122f`, `load_dptr_ffff_into_0d0d` | `0x717F`, `0x9AD0`, `0xC1F3` | `0xFFFF` |
| `set_dptr_fffd_and_call_122f`, `call_122f_with_dptr_fffd_6f96`, `call_122f_with_dptr_fffd_cc36` | `0x6F99`, `0x7048`, `0xCC39` | `0xFFFD` |
| `load_dptr_fffe_into_0d0c`, `call_122f_with_dptr_fffe`, `dptr_fffe_then_122f_at_e323`, `dptr_fffe_then_122f_at_e4d0` | `0xB07C`, `0xC1E0`, `0xDC2C`, `0xE326`, `0xE4D3` | `0xFFFE` |

(`pd,7059,call_122f` is an annotated store-back site whose name carries no
immediate, and §4.1 is what it is about.)

Two things follow. **The repository's own naming convention already reads these
as "set DPTR to a near-`0xFFFF` constant"**, which is the same observation this
file reaches by census, arrived at one function at a time. And **this file is
not the first to notice** — it is reading that naming pattern across a
population no single annotation row can see.

### 4.3 The `entry_pick` groups

`entry_pick` is a heuristic — the nearest preceding call target by byte scan, not
a function boundary — but it is still a check on the distribution. If the loads
were scattered noise from unrelated code, sites sharing a pick would not agree
on what they load. They largely do: the nine sites under pick `0x007A` **all**
load `0xFFFC`, and the eight under `0x10E8` load `0xFFFF`/`0xFFFD`. Across the
whole table most multi-site picks carry a single displacement, and 69 of the 81
rows frame from all 24 anchors.

## 5. What this supports, and how strongly

**The running base is a displacement base into a record-like structure that the
firmware walks by small negative offsets — not a relocated table base.**

That sentence is an **inference from the displacement distribution**, and it is
labelled as one, in three specific ways:

- **It is an inference, not a decode.** The bytes name the offsets the firmware
  adds; they do not name the thing being indexed. `dptr_signed` is *a reading of
  the immediate* — the same 16 bits with bit 15 taken as a sign — and it is what
  makes two rows comparable. It is not evidence that the firmware sign-extends,
  or that it treats the immediate as a displacement rather than as an address
  near one.
- **The inference is the distribution, not any single site.** A single site
  loading `0xFFFC` means nothing, and several are already annotated in `main`
  (§4.2). Eighty-one clustering in a narrow band against a whole-region
  baseline of one in thirteen means something, at the strength of a
  byte-pattern count over a committed image.
- **It does not name a structure, and "record-like" is as far as it goes.** The
  issue's calibration paragraph asked for exactly this: not upgraded to "the
  base is a base of X" without naming the sites that carry it. The sites are
  named — one row each in `ec/annotations/pd-store-back-dptr-sites.csv`.

The reason the distribution reads as a cursor rather than a table base is the
**sign**. A relocated table base is loaded as an absolute address — a constant
per table, varying between tables, and nowhere near a 16-bit word's zero. These
immediates cluster around *zero* and lean *negative*, which is what a pointer
being offset from a base looks like, and is not what a base looks like. The
concentration at `-1`/`-4`/`-3` is what makes "walked" the right verb and
"indexed" the wrong one. The `0x1253` sites clinching it — every one of the 32
that resolves, positive, against 50 of 81 here — is the same distinction seen
from the other side: an *addend* moves forward, a *displacement from a cursor*
moves back.

## 6. What this does not establish

- **The structure's contents, width, or record count.** Nothing here decodes
  what any of these 81 sites is *for*. `pd-index-geometry.md` §5 stops at the
  same line for the `0x260` records — "A `0x260`-byte record with a `0x1F`
  sub-stride in a USB-PD controller could be a port context, a message log, a
  negotiation-state block or something else" — and this file stops one step
  earlier still: it does not know the record is `0x260` wide, or wide at all.
- **Whether the `0x260` stride is the same array. It is not, on this evidence.**
  `pd-index-geometry.md` §3.2's `0x260` is a **stride between records** —
  `Rn × 0x60 + Rn × 0x200`, an index multiplied by a record width. What this
  file reads is a **displacement from a cursor**. A cursor walked by `-1`, `-2`,
  `-3` is not the same construction as an index multiplied by `0x260`, and the
  resemblance is worth naming only so a reader does not have to notice it. **#1118
  stays separate**, and nothing here re-derives it.
- **That the 61 uncorroborated sites are calls.** The parent already names this
  two-sided blind spot for `0x1253`: a `12 12 2f` inside a data table is
  indistinguishable from an `lcall 0x122F`, and a call through a dispatch table
  carries no target bytes at all. What is new here is only that the corroborated
  rows behave like the rest, so a reader who wants sites that are certainly
  calls can take the `both` rows and a reader who wants the full population has
  the remainder, labelled.
- **That gap 3 means the load executes.** §4.1 is the boundary: for 19 rows a
  decoded listing confirms the pair sits inside one function; for the other 62
  only the byte stream says so, and control flow is not recovered here.
- **A phantoms verdict for this population.** The parent names four phantom
  writers at §3 and labels rather than filters them. **This file does not
  classify the 81** — framing counts are printed per row and a row that scores
  low is printed with its count beside it. Where this reading could be wrong is
  in the uncorroborated rows, and §4's three checks are what bound that, not a
  filter.
- **`entry_pick` is a heuristic and rows that disagree are read as
  disagreeing.** A `12 hi lo` inside a data table is indistinguishable from an
  `lcall`. §4.3 uses the picks as a coherence check, not as function boundaries.
- **Nothing about the EC's `0x0D`/`0x0E`.** See the header. The `image` column
  in the committed table says `pd` on every row so a row cannot be quoted as an
  EC claim.
- **Nothing observed on hardware.** No register was read back, no write was
  attempted, nothing was run on the machine. Static analysis of a committed
  image. The displacement a site *executes* with is a runtime question these
  bytes do not decide.
- **Nothing runs this tool in CI, and that is deliberate.** The branch's push
  token has no `workflow` scope, so registering `--check` in
  `.github/scripts/agent-gates.sh` would fail at the end of the run rather than
  the start — the parent's §6 says the same of itself. What this change does
  instead is hold the `--check` in `ec/tools/test_pd_store_back_dptr.py`, which
  is what `pd-direct-offset-sites-hold.md` records as the gap the sibling left.

## 7. What a human with the machine would settle

The distribution is a static reading of what the firmware *loads*. Two
observations from hardware would decide what the reading means, and both are
outside what this pipeline can reach: what the pair holds immediately before a
given store-back site executes, and whether the addresses those displacements
name are contiguous. The first is a register read over the EC's own trace path;
`docs/hardware-tests/` carries that procedure shape for the EC side. The second
follows from the first, and neither is a reason to hold back the static half —
this is what the bytes settle, and it is now settled.
