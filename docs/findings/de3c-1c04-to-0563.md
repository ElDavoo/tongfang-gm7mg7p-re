# The store at `bank1,0xDE96` writes the `0x1C04` byte to the address the `0x0564:0x0563` pair spells, and that pair is staged by the same routine from two CODE tables — an indexed set, not one address and not the caller's

(2026-09-28, issue #1296. Static reading of `ec/firmware/GMxMGxx_11.800`
through `ec/tools/r1r2_predecessor.py`. No capture opened, no EC, no
hardware, no Windows, no `registers.yaml` row touched.)

`docs/findings/dptr-rebuild-walk-guard.md` §2 recorded the pointer at the
`movx @DPTR,A` as "whatever the caller *above* `0x8A04` left in those
registers" and §7 listed the address under **Not established, and not
guessed.** Both are corrected in place in that file; this is the evidence.

Read the title's "an indexed set" with §3's condition attached: the 103
addresses are the set **if** `0xDE3C`'s staging arm is the last writer of
`0x0563`/`0x0564` before `0xB6DE` reads them, and no committed tool
establishes that it is. §6 names the gap and §3 states the condition where
the table is.

## 1. What `R2:R1` holds at the store

```asm
; ec/decompiled/bank1/DE3C.asm:50
de8e     90 1c 04 mov      DPTR, #0x1c04
de91     e0 - -   movx     A, @DPTR
de92     8a 83 -  mov      DPH, R2
de94     89 82 -  mov      DPL, R1
de96     f0 - -   movx     @DPTR, A
```

```console
$ python3 ec/tools/r1r2_predecessor.py ec/firmware/GMxMGxx_11.800 --at 0x15E96
bank1:0xDE96   movx @dptr,a
  DPH  = XDATA 0x0564
        DPH <- R2 <- A @ 0xB6E6
  DPL  = XDATA 0x0563
        DPL <- R1 <- A @ 0xB6E1

  paths walked 34, pruned 1, not followed 2
  pruned        bank1:0xB726  0xB726 sets CY=0x01, but this path carries CY=0
  not followed  bank1:0xB6F3  0xB6F3 reads as a ret but the flow decode never reached it
  not followed  bank1:0xB706  0xB706 reads as a ret but the flow decode never reached it
```

**The high byte is the byte at XDATA `0x0564` and the low byte is the byte at
XDATA `0x0563`** — the *contents* of those two bytes, not their addresses and
not the caller's values. Both are last written inside the callee:

```asm
; ec/decompiled/bank1/B6DE.asm:7
b6de     90 05 63 mov      DPTR, #0x563
b6e1     e0 - -   movx     A, @DPTR
b6e2     f9 - -   mov      R1, A          ; R1 := XDATA 0x0563
b6e3     90 05 64 mov      DPTR, #0x564
b6e6     e0 - -   movx     A, @DPTR
b6e7     60 3d -  jz       0xb726
b6e9     fa - -   mov      R2, A          ; R2 := XDATA 0x0564
```

**This is not the caller's pointer, and it is not `0x0563`.** `f9` is
`mov R1,A`; the address `0x0563` is what `DPTR` held for the `movx`, and what
lands in `R1` is the byte that read returned. A reading of the three
instructions as "`R1` becomes `0x0563`" is the one this file was opened to
correct, and the correction goes the other way from what the opening expected:
the answer is neither a caller-supplied pointer nor a single fixed address,
but **a 16-bit value the firmware itself staged**, whose set of possible
values §3 enumerates from the committed bytes.

The old walk's blind spot is now nameable. It read the six address ranges
above `0xAC36` and found no instruction writing `R1` or `R2` — which is
true, and was never the question. The clobbering instruction is a **callee**,
reached over the `lcall 0xB6DE` at `0xDE89` (`ec/decompiled/bank1/DE3C.asm:48`),
twelve bytes below the store, and a linear window cannot cross that edge: it
stops at the first control-flow instruction. `trace_xdata_refs.walk()` is
exactly such a window, and §1 of
[`dptr-rebuild-walk-guard.md`](dptr-rebuild-walk-guard.md) is the census of
what widening its guard could and could not reach.

## 2. Why the answer does not depend on which path arrived

Two facts, both checked rather than assumed.

**Nothing branches into `0xDE8E`.** A whole-image scan of every `sjmp`,
`jc`/`jnc`/`jz`/`jnz`, `jb`/`jnb`/`jbc`, `cjne`, `djnz`, `ajmp`/`acall`,
`ljmp`/`lcall` in the three main-EC regions, resolved and compared against
`0xDE8E`, returns **no** incoming edge. The store is reached only by falling
through `jc 0xDE9E` at `0xDE8C` **not taken**, i.e. with carry clear.

**The 8051 saves no registers across a call.** `lcall` pushes a return
address and nothing else; `R0`–`R7` belong to whichever frame is running.
`0xB6DE` never pushes them, so on every path that reaches the store the
values in `R1` and `R2` are whatever that callee left — which is why the
walk has to enter it rather than step over it.

Together those make the single clobbering point dominate every arrival path,
which is the reason a *caller-side* walk contributes nothing to the answer
even now.

### The carry guard is what makes it sound, and it is not the `jz`

`0xB6DE` has three `ret`s. `setb CY` at `0xB726` is reached from three
places, and **only one of them skips `mov R2,A`**:

| predecessor of `0xB726` | reached when | did `mov R2,A` run? |
|---|---|---|
| `jz 0xB726` at `0xB6E7` | `XDATA 0x0564 == 0` | **no** |
| `jc 0xB726` at `0xB6F2` | `XDATA 0x0564` is 1 or 2 (`subb A,#4` borrows, and the `cjne` at `0xB6EA` already excluded 0 and 3) | yes |
| `cjne A,#0x30,0xB726` at `0xB721` | `XDATA 0x0564` is 4 and `(XDATA 0x0563 & 0xF0)` is not one of `0xA0`/`0xB0`/`0x20`/`0x30` | yes |

So the naive reading — "the only arm that sets carry is the one the `jz`
enters" — is **false on the bytes**: two of the three carry-setting returns
have `R2` defined. What rescues the answer is the caller's `jc 0xDE9E`, which
excludes *all three*. Had the call branched the other way, the high byte
would be genuinely unconstrained and the tool says so rather than naming a
value; `ec/tools/test_de3c_store_target.py`'s inverted-guard fixture is
exactly that case, and it is the negative that would falsify this file.

`R1` is not conditional in the same way: `mov R1,A` sits *before* the `jz`,
so every return has it.

## 3. The address, as a set read out of the two CODE tables

`0x0564` and `0x0563` are written by `0xDE3C` itself, on the arm taken when
`XDATA 0x1C00` is zero, from two 128-byte CODE tables indexed by
`0x0561 & 0x7F`:

```asm
; ec/decompiled/bank1/DE3C.asm:23
de5b     90 05 64 mov      DPTR, #0x564
de5e     f0 - -   movx     @DPTR, A     ; 0x0564 := CODE[0xDD3C + (0x0561 & 0x7F)]
de5f     ed - -   mov      A, R5
de60     90 dd bc mov      DPTR, #0xddbc
de63     93 - -   movc     A, @A+DPTR
de64     90 05 63 mov      DPTR, #0x563
de67     f0 - -   movx     @DPTR, A     ; 0x0563 := CODE[0xDDBC + (0x0561 & 0x7F)]
```

Those two tables give the store's target set **conditional on `0xDE3C`'s
staging arm being the last writer of the pair** before `0xB6DE` reads it. No
committed tool discharges that condition, and §5 says why: a store through a
register-built DPTR is not a site either sweep can see, and neither
`trace_xdata_refs.py` nor `find_indirect_xdata.py` was able to rule such a
writer out. §6 carries the condition in full. What follows is therefore the
union over the two tables' indices, not a proven whole.

The table at `0xDD3C` holds `0x03` throughout except `0x05`, two `0x09`s and a
run of twenty-five `0x00`s at the end; the table at `0xDDBC` holds `0x00`–
`0x5F` for the first ninety-six entries, then
`0xC0 0x14 0x99 0x98 0xCA 0xC9 0xB5`, then twenty-five `0x00`s. Reading the
high byte from the first and the low byte from the second:

| the store at `0xDE96` can write, given that staging | indices |
|---|---|
| `0x0300`–`0x035F`, the contiguous run | 0–95 |
| `0x0398`, `0x0399`, `0x03B5`, `0x03C0`, `0x0514`, `0x09C9`, `0x09CA` | 96–102 |
| `0x0000` — **excluded** | 103–127 |

The exclusion is the same `jz` from §2 and the same `jnz 0xDE5B` at `0xDE56`:
both reject exactly the indices whose `0xDD3C` byte is zero, and those are
exactly the indices that would make the store write XDATA `0x0000`. So the
store never writes page zero, and the reason it does not is the carry guard
rather than a coincidence in the tables.

`0x0561` is incremented at `0xDE81`–`0xDE88` *before* the call, so the pair
in hand is the one staged on the last invocation that took the `0x1C00 == 0`
arm. Which invocation that is does not narrow the set: the index is not
pinned, so the table above is the union over every index the staging arm
admits.

## 4. What the store is

**A write-back of the `0x1C04` staging byte into the `0x0563`/`0x0564`
pair, followed by `0x1C00 = 0xFF`** — a write-then-clear, the same shape as
`bank1,0xE2C3` (`set_1c00_ff_clear_1c04_1c05`) and `bank1,0xE27D`, and
consistent with `ec/annotations/xdata-086x-dispatch.md` §6's reading that the
`0x086x` copy is not a mirror. The gate into the block is `0x1C00`: the
routine's own first test is `jnz 0xDE75` on it, and the arm that reaches the
store additionally requires bit 1 of that byte set and bits 2–6 clear, so
`0x1C00` is `0x02` or `0x03` when the store runs.

### The `0x086x` candidate, ruled out

Issue #1296 proposed that the store's target is one of the `0x0866`–`0x086B`
staging bytes, because `bank0,0xD28E` (`copy_0866_86b_to_1c04_1c3a`) copies
`0x0866`→`0x1C04` and the store is the reverse direction of that first pair.
The direction is right and the address is wrong: the target is the pair's own
value, and that value is out of page `0x03`, not page `0x08`. No index in
§3's tables produces an address in `0x0860`–`0x086F`.

### `param_1`/`param_2` are a naming artifact, not a second witness

`ec/decompiled/bank1/DE3C.c:50` reads
`*(undefined1 *)CONCAT11(param_2,param_1) = DAT_EXTMEM_1c04;`, and the issue
took the decompile as agreeing that `R1`/`R2` are arguments. Ghidra named the
routine's **incoming** `R1`/`R2`; the store reads the values those registers
hold *after* `0xB6DE` overwrote them. The decompile is not a witness here
either way — it is the same instructions, with the caller's naming attached
to the wrong end of the chain. This resolves the issue's "done" criterion by
a route it did not offer: not "named from the call sites", not "caller-supplied
with per-caller values", but **not the caller's values at all**.

## 5. The blind spot, and the census this does not join

`trace_xdata_refs.py` over these two addresses reports four sites, and the
store is not one of them:

```console
$ python3 ec/tools/trace_xdata_refs.py ec/firmware/GMxMGxx_11.800 0x0563 0x0564 --csv
0x0563,0x136DE,bank1,0xB6DE,24,0,read x1,"movx a,@dptr ; mov r1,a"
0x0563,0x15E64,bank1,0xDE64,23,1,write x1,"movx @dptr,a ; mov a,#0xa1"
0x0564,0x136E3,bank1,0xB6E3,24,0,read x1,"movx a,@dptr ; jz +0x3d"
0x0564,0x15E5B,bank1,0xDE5B,24,0,write x1,"movx @dptr,a ; mov a,r5"
```

That is the gap class in one line: **a DPTR assembled from a register pair is
not a `MOV DPTR,#imm16` site**, so the store at `0xDE96` is a third access to
`0x0563` that no site table carries, and a reader taking those four rows as
the account of `0x0563`'s accesses would be wrong by one.
`find_indirect_xdata.py` does not close it either, and by design: it covers
`movx @Ri`, whose page is in `P2` and whose low byte is in the register.
`r1r2_predecessor.py`'s docstring says so in its own first paragraph, so the
next reader does not assume the sweep already happened.

Two further blind spots, both of which the answer survives:

- **The `0x8A04` frame cannot be re-read from a committed file.**
  `bank1,0x8A03` is a one-byte `ret`, `bank1,0x89F4` ends at `0x8A02`, and
  nothing in `index.csv` or any committed listing covers `0x8A04`–`0x8A26`.
  The old walk read those bytes by hand; the frame is not reproducible from
  the tree. It is also not needed, which is §2's point stated the other way
  round.
- **Only `0xAC40` as a *recorded direct* transfer into `0xDE3C`.**
  `ec/annotations/bank-call-targets.csv` holds exactly one row whose `target`
  is `0xDE3C`, the `ljmp` at `0xAC40`. That is a statement about the table,
  not about every path that reaches the routine, and §2's argument does not
  use it.

## 6. What this does not establish

- **Nothing about what the EC does with any of the 103 bytes.** Every input
  is a committed file. A store site says the firmware can write an address;
  whether the EC acts on it, and what it means, needs a live observation at
  the machine. None is made here and none is available from this runner.
- **Nothing about the `0x0561` index's value at the time of the store.** The
  set is the union over the indices the staging arm admits. Narrowing it
  needs a read of `0x0561` on hardware.
- **That `0xDE3C`'s staging arm is the *last* writer of `0x0563`/`0x0564`
  before `0xB6DE` reads the pair.** §3's 103 addresses are the set
  *conditional on* that, and no committed tool establishes it. The only
  evidence offered anywhere in this file is §5's four
  `trace_xdata_refs.py` rows, and §5 states in the same breath that a DPTR
  assembled from a register pair is not a `MOV DPTR,#imm16` site — which is
  precisely the class `0xDE96` belongs to. `find_indirect_xdata.py` is the
  other addressing mode, `movx @Ri`, whose page is in `P2`; it returns no row
  for either address either (§9 step 4). So the class is **unexamined, not
  cleared**: if any other routine writes either byte through a register-built
  DPTR, the set is wider than 103 and unbounded. Discharging the condition
  needs a sweep that sees the register-built case, or a hand-checked list of
  the other writers.
- **The other two `RET_OPCODES`' paths are only as good as the carry
  argument.** If a future `setb CY` is added to `0xB6DE` on a path the
  caller's `jc` does not exclude, the high byte becomes unconstrained and the
  tool will say `not written on some path followed` rather than name a value.
  `test_de3c_store_target.py` holds that behaviour against a fixture, not
  against this image.
- **A general register def-use analysis of the 8051.** There is no calling
  convention to model; the claim is scoped to the paths this tool followed,
  with carry as the only condition it carries.
- **`registers.yaml` rows for any of the addresses named here.** None of
  `0x0563`, `0x0564`, `0x0561`, `0x054C`, `0x1C00`, `0x1C04` or `0x0490` has
  one, checked against all 176 rows. A new row is a `status:` decision with a
  `static_refs` census behind it, gated by `check_register_counts.py` and
  `check_status_vocabulary.py`; the `0x1C04`/`0x1C05` pair belongs to the
  sibling follow-up that is creating those, and duplicating them here would
  only collide. **Named follow-up, not a row invented here.**
- **The pair's *addresses* and the pair's *values* are different questions,
  and only the first is clean.** The seven names above are undocumented. The
  103 addresses §3 enumerates are not all in the same position: `0x030E` and
  `0x030F` — table indices 14 and 15 of the contiguous run — already carry
  rows, both `SBS_CHARGING_VOLTAGE` at `present-untested` with
  `static_refs [4, 1]`. So a claim that the store's targets are all
  uncharacterised bytes would be false by two, and a claim that *the
  addresses involved* are all undocumented is true only because it names the
  pair rather than its values. Which of the 103 is written is static; what
  any of them means is not, and `present-untested` on `0x030E`/`0x030F` is
  exactly the status that says so.
- **`ec/annotations/xdata-1c3x-consumers-sites.csv` gains no `0x1C04` row.**
  It carries none today, because it was generated from an eleven-address list
  that does not include `0x1C04`; widening it moves counts and belongs with
  whoever creates the `registers.yaml` row.
- **Any hardware or Windows step.** None is needed and none is claimed. No
  capture was opened, no register read back, no EC or HID node touched. The
  toolchain is `python3` and the committed firmware: no Ghidra, no
  `analyzeHeadless`, no `ilspycmd`, no radare2.

## 7. What this change regenerates, and what it moves

Seeding three annotation rows means re-exporting, because a row that names a
function has to reach the listing and the decompile. Default mode only --
`--work` scratch, the committed `ec/ghidra/project/` untouched, no
`--mode rebuild-project`.

- `ec/decompiled/bank1/{DE3C,B6DE,8F6B}.{asm,c}`, `index.csv`,
  `listing-index.csv`, `ec/ghidra/manifest.csv`, `c-digests.csv` and
  `cross-decoder.csv`, all by their own tools.
- `ec/annotations/function-groups.csv`, `call-graph-callees.csv`,
  `xdata-registers.csv`, `xdata-clusters.csv` and `xdata-export-ownership.csv`,
  all by their own tools. `function-groups.csv` is the one worth reading
  twice: annotating `0x8F6B` **merges two call-graph components**, so
  `callgraph_bank1_98CC` is gone and its two rows have moved into
  `callgraph_bank1_1738`, which is why that file's diff is large and almost
  entirely one figure in a repeated comment.
- The 24 `.c` files this export also rewrote, for the reason the next bullet
  gives. They are not this issue's finding; they are the export catching up
  with a symbol table that had been committed without one.
- `ec/annotations/subsystems.md`'s four census bullets and its `bank1` table
  row, which `build_ec_decompile.py --check` recounts rather than trusts.

**Two census pins in shared tools moved, and both are the pattern their own
comments describe** — a pin that exists so a change adding a row on purpose has
to say so:

- `build_ec_decompile.py --self-test`: 1,957 -> 1,960 rows, bank1's
  `annotations_applied` 721 -> 724 and `functions_named` 605 -> 608, sum
  1,978 -> 1,981.
- `xdata_register_map.py --self-test`: the `DAT_EXTMEM_` tally
  1021/8675 -> 1015/8623 and the symbol tally 161/6147 -> 167/6199. **This one
  is mostly not #1296's doing.** Re-exporting the three functions is the first
  export this tree has run since issue #250's nine `XDATA_*` symbols landed in
  `xdata-symbols.csv` without one, so their renames reach the `.c` text at
  last and the `DAT_EXTMEM_` half falls by 52 across 25 files. The arithmetic
  is the check: 8632 raw against 7765 main-EC and 858 PD leaves
  `extmem_commented` at 9, the PD half and `extmem_both` are unmoved, and the
  full address/reference census does not move at all -- only which token spells
  them. A half-re-export cannot satisfy the tool's disjointness assertion at
  all (`0x07A4` would be spelled `GC6S` in the one new file and `DAT_EXTMEM_`
  in the 24 old ones), which is why the export was run whole rather than
  trimmed to the three.

## 8. Two follow-ups this work did not fold in

- **`disasm8051.mnemonic()`'s direct/A split is off by one in the prose
  beside it.** `dptr-rebuild-walk-guard.md` §3 names `0x54`/`0x44`/`0x64` as
  the `anl`/`orl`/`xrl direct,#imm` forms; on the 8051 those are the
  `A,#data` forms and the direct ones are `0x53`/`0x43`/`0x63` — which is
  what `disasm8051.OPCODE_LEN` has (three bytes) and what
  `find_indirect_xdata.P2_WRITERS` has. `r1r2_predecessor.py` keys its writer
  table on bytes for that reason and
  `test_de3c_store_target.py::WriterTableIsKeyedOnBytes` holds the two
  spellings apart. The file is left as it is: the correction belongs with
  whoever fixes the mnemonic table, and this change has no business growing
  that file's §3.
- **The `0x8A04` frame has no committed listing**, so the frame the old walk
  read by hand cannot be re-derived. Seeding one needs
  `--mode rebuild-project`, which two branches cannot both do. Not needed for
  the answer; worth a listing for its own sake.

## 9. Reproducing it

All of it, from the repository root. No Ghidra, no network, no hardware.

```sh
# 1. the pointer, and the prune that makes it a single answer
python3 ec/tools/r1r2_predecessor.py ec/firmware/GMxMGxx_11.800 --at 0x15E96
python3 ec/tools/r1r2_predecessor.py ec/firmware/GMxMGxx_11.800 --at bank1:0xDE96 --csv

# 2. nothing branches into 0xDE8E, and the 0xB6DE entry is the only one
python3 - <<'EOF'
import sys
sys.path.insert(0, "ec/tools")
from disasm8051 import (OPCODE_LEN, REL_OPCODES, inline_arg_len, paged_target,
                        relative_target)
from trace_xdata_refs import REGIONS
d = open("ec/firmware/GMxMGxx_11.800", "rb").read()
want = {0xDE8E, 0xDE96, 0xB6E9, 0xB6DE}
hits = {w: [] for w in want}
for name, lo, hi, base, _ in REGIONS:
    if base is None:
        continue
    i = lo
    while i < hi:
        op, n = d[i], OPCODE_LEN[d[i]]
        if i + n > hi:
            i += 1
            continue
        addr = base + (i - lo)
        if op in (0x02, 0x12):
            t = (d[i + 1] << 8) | d[i + 2]
        elif op in REL_OPCODES:
            t = relative_target(op, d[i + OPCODE_LEN[op] - 1], addr)
        elif op & 0x1F in (0x01, 0x11):
            t = paged_target(op, d[i + 1], addr)
        else:
            t = None
        if t in hits:
            hits[t].append((name, addr, op))
        i += n + inline_arg_len(d, i)
for w in sorted(hits):
    print(f"{w:#06x}: {hits[w]}")
EOF
# 0x0b6de: [('bank1', 56969, 18)]   <- the one lcall, at 0xDE89
# 0x0de8e: []                        <- nothing branches into the block
# 0x0de96: []
# 0x0b6e9: []                        <- mov R2,A is only reached by falling through

# 3. the two CODE tables, and the address set §3 tabulates
python3 - <<'EOF'
d = open("ec/firmware/GMxMGxx_11.800", "rb").read()
off = lambda rt: 0x10000 + (rt - 0x8000)      # noqa: E731  bank1 CODE
high = d[off(0xDD3C):off(0xDD3C) + 128]       # -> XDATA 0x0564 -> DPH
low = d[off(0xDDBC):off(0xDDBC) + 128]        # -> XDATA 0x0563 -> DPL
targets = sorted({(h << 8) | l for h, l in zip(high, low) if h})
print(len(targets), "addresses;",
      "0x0000 excluded:", 0 not in targets)
print(" ".join(f"{t:#06x}" for t in targets))
EOF

# 4. the gap: the store is not a site either sweep can see
python3 ec/tools/trace_xdata_refs.py ec/firmware/GMxMGxx_11.800 0x0563 0x0564 --csv
# and the other addressing mode, movx @Ri, over the whole image -- no row for either address
python3 ec/tools/find_indirect_xdata.py ec/firmware/GMxMGxx_11.800 --csv | grep -iE '0x0?56[34]'

# 5. the suites, this work's and the runner's total
python3 -m unittest discover -s ec/tools -p test_de3c_store_target.py
bash tools/run-tests.sh
```
