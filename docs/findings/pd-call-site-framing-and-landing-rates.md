# PD control-flow call sites: framing and landing rates

## Summary

The PD image's rel8 (relative branch) and paged (ajmp/acall) call sites have been analyzed against the committed Ghidra decompiled listings under `ec/decompiled/pd/`. Of the distinct control-flow targets identified by static analysis:

- **Relative (rel8) branches**: 4369 distinct targets, 39 with committed listings (**0.9%** landing rate)
- **Paged branches (ajmp/acall)**: 1177 distinct targets, 22 with committed listings (**1.9%** landing rate)

(Measured with `ec/tools/pd_call_site_analysis.py --csv` against `ec/firmware/GMxMGxx_11.800` and `ec/decompiled/pd/*.asm`)

## Three possible readings

Issue #1690 named three explanations for a low landing rate:

1. **Missing decompilation**: The PD's control flow genuinely concentrates in bytes the repository's Ghidra listings do not yet cover. The program is understood at ~0.9-1.9% of its reachable targets.

2. **Base/offset framing error**: The committed listings are misframed or misbased relative to the runtime addresses the walk computes. The `REGIONS` entry for `pd-image` specifies base `0x0000`, so a file-offset/runtime slip would appear here and nowhere else in the audited regions.

3. **Walk defect**: The `relative_sites()` or `paged_sites()` functions in `audit_call_targets.py` mis-frame the PD image — either the region bounds are wrong, or the runtime address computation does not match the PD's actual loader layout.

## What the data does and does not say

**Does not settle**: The data measures the *agreement* between two sets of addresses — control-flow targets from static analysis and Ghidra listing filenames. Agreement is not the same as correctness. Low agreement could mean the listings are wrong, the walk is wrong, or both are right but the listings are incomplete.

**Does say**: The landing rate is consistently low for both rel8 and paged families (0.9-1.9%), which is plausible under reading (1) if the decompilation effort has focused on high-reachability entry points and not on all reachable bytes. The rates are much lower than the audited main EC banks (4.5-13.3% for rel8, 6.9-13.3% for paged; see #1685 and the `audit_call_targets.py` self-test), which suggests the PD's listings are sparser or sparser relative to what the walk finds.

## What would settle each

To pick between the three readings:

**For (1) — missing decompilation**: Run `pd_call_site_analysis.py` on the updated tree after more Ghidra work and check whether the landing rates move toward the main EC's rates. That would show the targets themselves are valid and the walk is correct. Conversely, if rates stay flat despite seeding new listings at the 4000+ unreached targets, suspect (2) or (3).

**For (2) — base/offset framing**: Check the PD loader's actual runtime layout via hardware observation or by reading the bootloader's mapping code. Verify that the runtime base in `REGIONS` matches what the hardware does. Then re-measure: if the rates jump toward the main EC's rates with a corrected base, reading (2) was true. If not, suspect (1) or (3). (This is issue #1685's territory.)

**For (3) — walk defect**: Spot-check a few resolved targets by hand, reading the firmware bytes at those offsets and verifying the instruction makes sense as a control-flow target (a function entry, a common return point, etc.). Use `make_bank_image.py` or the raw `ec/firmware/GMxMGxx_11.800` dump to read the bytes. If the targets are valid code, suspect (1) or (2). If the targets land in data or erased bytes, the walk is misconfigured.

## Assumptions

- `relative_sites()` and `paged_sites()` correctly identify all statically-resolvable call sites in the PD region.
- Target addresses are computed correctly by `relative_target()` and `paged_target()`.
- The region bounds (0x20000-0x30000 file offset, 0x0000-0x10000 runtime address) are correct.
- Ghidra listing filenames (e.g., `0x06EA.asm`) are in runtime address space and correspond to the `target` values the walk computes.
- The PD image's loader uses the same Keil banking model (or a simpler flat model) and loads the image with base 0x0000.

```bash
python3 ec/tools/pd_call_site_analysis.py ec/firmware/GMxMGxx_11.800 --csv
```
